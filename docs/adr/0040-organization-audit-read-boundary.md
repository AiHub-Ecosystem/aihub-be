# Organization audit read boundary

Status: accepted

The durable trail [ADR-0035](0035-organization-audit-trail-boundary.md) established is now readable. `GET /v1/organizations/:organizationId/audit-events` returns one Organization's recorded acts at the Bearer boundary, newest first, to active owners and admins. That ADR settled the read policy in advance so its absence stayed a scheduled gap; this one records what the implementation had to decide beyond it, and is separate rather than an amendment because ADR-0035 is accepted, describes the write path, and is already being edited by the ordering-contract work in [#126](https://github.com/AiHub-Ecosystem/aihub-be/issues/126).

A suspended Organization stays readable, and this is the decision a future reader is most likely to mistake for an oversight. Both sibling Organization-scoped management reads deny it: the open-invitation listing and the API-key listing each refuse a suspended Organization, and the latter carries a comment explaining that it follows the invitation listing rather than the self-roster. The originating issue justified readability by citing the Organization Roster, which does not hold — the Roster is the caller's own view across every Organization and is a different shape entirely. The justification that does hold is that those two are management surfaces and this is evidence. Suspending an Organization should close the surfaces through which it acts; closing the record of how it acted means suspension erases the trail at the exact moment someone needs to read it, and an owner investigating their own suspension has nowhere else to look. The use case therefore has no `organizationStatus` branch at all, rather than one that reads the status and ignores it, and carries a comment pointing here so the absence is legible.

Every refusal returns one message. The read follows the open-invitation listing, which passes a single constant into the membership check and raises the same constant for the role refusal, rather than the API-key listing, which emits three distinguishable messages and thereby tells a caller who guessed an `organizationId` that the Organization exists and is suspended. That is a real leak in the sibling and is tracked separately in [#131](https://github.com/AiHub-Ecosystem/aihub-be/issues/131); it is named here because the two endpoints will be read side by side and the difference must not look accidental. Audit is the read where the distinction matters most: an endpoint that answers differently depending on tenant state is an Organization prober.

The durable `target_id` is not published, which is a stronger position than the originating issue asked for. The issue required that no User Account ID appear in the response; for a `membership` target, `target_id` _is_ the target's User Account ID, so publishing the column would have violated that requirement directly rather than subtly. Publishing it only for non-membership targets was rejected as a shape that varies by `target_type` for a field no client can follow anywhere — there is no foreign key to join it against, by ADR-0035's own design. `target_type` says what kind of thing was acted on and `target_label` says which one, in the words it carried at that moment, which is the pair a human reads. `organization_id` is omitted per event for a duller reason: it is in the path and identical for every row.

`detail` passes through as an open object rather than being re-whitelisted per action. The write path already constrains it structurally: nothing reaches the column except through the closed union of per-action drafts, which is precisely why serialising an input object — the ordinary way a credential reaches a table nobody can edit — has no expression there. A second whitelist on the read would state the same truth in a second place and would need editing for every Audit action that ships, doubling the work of the thing it claims to protect. The cost is a less precise published schema at that one field, and it is the only field where the contract is vaguer than the data.

Pagination is keyset on `(occurred_at, id)` descending, which is what the existing `(organization_id, occurred_at DESC)` index was sized for, so no migration and no index ship here. Offset was rejected because the trail grows while a reader pages through it and an offset page shifts under them — the failure mode being a control-plane act that is silently never shown. The cursor is a base64url payload carrying a version marker, the position, and a truncated hash of the active filter. The filter hash exists so that replaying a cursor under different filters fails loudly instead of paging through a different result set; it reuses the canonical-JSON-plus-SHA-256 helper the idempotency fingerprint already relies on, so the codebase keeps one answer to turning an object into a stable string, and it sorts the action list because the same filter typed in a different order is the same filter. It is not a forgery control and does not need to be: the cursor carries no authority, and every position it names is still bounded by the caller's Organization inside the query. A malformed cursor, an unknown version, and a filter mismatch all answer `INVALID_REQUEST` rather than earning a new error code, because all three have one recovery — drop the cursor and read from the start.

The cursor deliberately does not encode the identifier alone. An `oae_` id's first 48 bits are the millisecond of `occurred_at`, so ordering by id would today produce the same sequence as ordering by the pair, and a cursor could be half the size. That equivalence is a hidden coupling between the id generator and the read query, and it is exactly the class of assumption that already failed here once: the originating issue's premise that the identifier was time-ordered was false when written, because the store built ids from a plain `ulid(occurredAt)` that randomised everything after the millisecond prefix. The write path now uses the monotonic factory and the premise holds, but the read is written so that it would remain correct if the generator changed again. The guarantee is also process-scoped — two instances writing in the same millisecond still tie, with an arbitrary but stable order — so it is a property to lean on lightly rather than to restate as an absolute.

Page size is refused outside `1..200` rather than clamped. A silently shortened page is indistinguishable to a client from the end of the trail, and "the trail ends here" is the one thing this endpoint must never say wrongly. The window is half-open `[from, to)` with both bounds independently optional: the usage completeness report requires both because a window is the substance of a report, while here the default question is "what happened recently" and forcing an invented start date is friction that buys nothing. There is no maximum span and no clamp against the 24-month retention — retention enforces itself, an older bound simply matches fewer rows, and the cursor already bounds the cost of any single request.

Query parameters are parsed by hand at the presentation boundary rather than by a canonical TypeBox schema, which departs from the rule in `.claude/rules/presentation.md`. That rule was written for mutation bodies, where TypeBox already owns validation and the input arrives as typed JSON. A query string is stringly-typed: `limit` arrives as text, and `action` arrives as a string or an array depending on how many times the key was repeated. A schema check alone rejects all of it, and making it work would mean introducing a coercion layer this repository has nowhere else. The single existing query-parameter precedent — the Speaking questions listing — parses by hand for the same reason. The contracts module still owns the response schema, as it does for every endpoint. This is the first path in the OpenAPI document to declare query parameters at all, and `action` is declared `explode: true` so a generated client repeats the key instead of comma-joining values the server would not parse.

Two test seams cover this and no new seam is introduced. The HTTP flow through the application module — the seam the API-key listing and invitation integration specs already use — covers authorization, refusal uniformity, filtering, validation, redaction, the absence of identifiers, and the full cursor round trip including filter mismatch and stale versions, all against the published contract schema. Because the cursor is observable end to end there, it gets no separate unit spec. Ordering and the keyset predicate are added to the existing audit-event database spec instead, on the same grounds that spec already states for the append-only trigger: a fast-lane assertion about `ORDER BY` would be evidence about a string, not about which row comes back first. That lane stays outside `pnpm verify`.
