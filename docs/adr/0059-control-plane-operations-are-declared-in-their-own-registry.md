# ADR-0059: Control-plane operations are declared in their own registry, not in the Operation Catalog

- Status: Accepted
- Related issue: #173
- Related: [ADR-0057](0057-graded-request-order-is-a-declared-contract.md), [ADR-0038](0038-bearer-management-idempotency-scope.md)

The Organization-scoped management routes kept their public contract in three places at once: a path literal in the route declaration, a hand-written path constant in the OpenAPI builder, and a hand-written list of the statuses that operation could return. Issue #173 asked for all of them to read one list. We built that list, then did not put it in the Operation Catalog. A Control-plane operation authenticates with a Bearer User Access JWT, carries no API-key Scope, resolves no User Identity, and dispatches nothing to an AI Service, so it has no downstream service, no downstream path, no downstream contract, and no metering mode to declare. `OperationId` is the dispatch vocabulary: `http-operation-dispatcher.ts` hardcodes one `dispatch()` overload per operation id, and the first downstream, scope, and metering guards all resolve an id against the catalog and read those fields. Widening `OperationId` with eighteen non-dispatch ids would force eighteen overloads for routes that never reach a dispatcher, and would leave every catalog consumer reading a field those entries do not have. So the two registries are separate by construction, the way the graded-request set is declared separately from the Operation Catalog for the same reason (ADR-0057). The Management operation registry owns each operation's path, method, success status, idempotency mode, organization resolution, request and response schemas, and error statuses; route declarations and the OpenAPI document read from it, and the Postman handover collection follows from the document. Parameter descriptions, response prose, and query parameter shapes stay with the builder's per-operation path items, because a Management operation's public difference from another is mostly exactly that prose.

## Considered options

One universal registry covering every Public API Route was rejected for the reason above, not for its size. A single flat entry with optional fields was rejected because the fields that would become optional are the ones every consumer reads: `downstream` is read by the metering service and the usage-completeness report, and `requiredScope` by the API-key guard and by `publishedScopes()`, which feeds API-key creation validation and the CLI's `--entitlement` list. Making them optional would push the check to each call site instead of the type. Reusing `identityScope: 'organization'` for the management routes was rejected: in the published document the field already carries three meanings, because the four dispatch operations report `user` with an `X-User-Identity` parameter, eighteen management routes report `user` with `BearerAuth` and no such parameter, and the sandbox assertion route reports `organization`. The field names the User Identity form an operation consumes, which no management route does, so the honest move was to leave it alone and to declare how each management operation learns its Organization through `organizationResolution` instead. Storing the OpenAPI path in the registry alongside the Nest path was rejected in favour of deriving it, because two spellings of one route is the drift this ADR exists to remove; `toOpenApiPath` converts `:organizationId` to `{organization_id}` in one place. Declaring `maxBodyBytes` and `timeoutMs` for management operations was rejected: the body-limit and timeout hooks key on an exact path, so a `:segment` path is silently never matched, and a declared limit that is never applied is worse than no declaration. Two guard tests now hold that line.

## Consequences

The builder keeps one path item function per management path, so a new management operation is still a hand-written function; what the registry removes is the second and third copy of its path and its status list. The generated document is byte-identical to the one published before this change, including the `Idempotent-Replay` descriptions, which stay operation-specific and are passed to the generator rather than declared once. Management operations deliberately carry no `maxBodyBytes` and no `timeoutMs`, so a management request is bounded only by Fastify's own ceiling; if a route ever needs a tighter bound, the hooks need pattern matching first, which is a separate decision. The `identityScope` comment in the Operation Catalog no longer promises an `'organization'` value, and `ARCHITECTURE.md`'s `timeoutMs` count rule still expects exactly the four dispatch entries because management operations declare none.
