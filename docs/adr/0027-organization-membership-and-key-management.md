# Organization membership, invitation, and API-key self-service boundary

Status: accepted

AIHUB will model access as an explicit relationship between an AIHUB User Account and an existing Organization. A user may belong to multiple organizations; management requests carry an explicit `organizationId`, while User Access JWTs remain free of organization and role claims. Membership roles are `owner`, `admin`, and `member`: owners and admins may invite, only the normalized invited email may accept, and pending invitations are separate from memberships. Invitations reuse the existing opaque hash-only, single-use token pattern with a 24-hour lifetime and one open invite per organization/email; resending invalidates the previous token. An active member invite is a conflict, an open invite is replaced on resend, and a disabled membership receives a new invite that may reactivate it. An unknown email follows the existing registration → verification → login → accept flow and never creates an account implicitly. Acceptance rejects disabled accounts, suspended organizations, and revoked/replayed tokens without consuming a still-valid token; token consumption and membership creation/reactivation are one transaction. Memberships use `active`/`disabled` state without physical deletion, and every organization must retain at least one owner; owner transfer, demotion, and removal are atomic. Owners have full membership and API-key authority; admins may manage ordinary members and API keys but not owners or admins; members have no mutation authority.

API keys remain organization-owned. Lists expose metadata only, and rotation preserves key metadata while atomically creating the replacement and revoking the old key; the raw replacement is returned once and there is no intentional grace window. Invite and rotation mutations reuse the existing idempotency seam. A suspended organization accepts no membership or key mutations. Organization creation and first-owner assignment remain operator-provisioned. The current Clerk sandbox remains until the cutover of [issue #94](https://github.com/AiHub-Ecosystem/aihub-be/issues/94) executes the supersession recorded in ADR-0046; Google federation is a separate issue. Durable audit history is intentionally deferred to [issue #92](https://github.com/AiHub-Ecosystem/aihub-be/issues/92).
