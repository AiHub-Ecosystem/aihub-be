# ADR-0016: Durable metering boundary and billing evidence

- Status: Accepted
- Related issue: #9

AIHUB records one durable internal metering record for each request after the API key has resolved the organization and key, including later assertion, validation, downstream, and internal failures; requests that never authenticate have no metering record. The record is written before the response, billability is limited to successful outcomes, and a metering write failure never changes a successful customer response. `request_id` is the uniqueness boundary; billable request units are binary and default to non-billable (deliberately overriding the earlier schema default of one), so an idempotency replay records evidence without charging a second request. Gateway validation/authentication and gateway rate-limit failures are client errors, downstream failures (including provider throttling) are downstream errors, and unexpected failures are internal errors.

AIHUB stores provider-reported aggregate usage and AI-processing timing through a sanitized internal telemetry DTO, never estimates tokens, and preserves valid partial values while classifying incomplete usage as `missing_usage` only when a model call completed without complete usage evidence. Requests that fail before a model call use `not_applicable`; `complete` requires valid input, output, and total aggregates; explicitly non-model operations also use `not_applicable`; and quota state that could not be verified uses `quota_unverified`. Timing fields come from the request lifecycle and dispatcher, while AI processing time is provider-supplied only. Current AI Services return aggregate token usage and `metrics.ai_processing_ms`; model identity is outside the provider contract and is not required for metering. Metering remains internal, so public response contracts do not change; provider usage telemetry is coordinated separately with the AI Service contract work.
