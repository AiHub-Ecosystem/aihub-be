# ADR-0104: Observe shared-host and dependency health

- Status: Proposed; the AIHUB owner approved the scoped collectors and resource ceilings on 2026-10-16. Runtime verification and catalog publication are recorded separately.
- Date: 2026-10-15
- Related issues: [#474](https://github.com/AiHub-Ecosystem/aihub-be/issues/474), [#237](https://github.com/AiHub-Ecosystem/aihub-be/issues/237), [#291](https://github.com/AiHub-Ecosystem/aihub-be/issues/291), [#298](https://github.com/AiHub-Ecosystem/aihub-be/issues/298), [#362](https://github.com/AiHub-Ecosystem/aihub-be/issues/362), [#412](https://github.com/AiHub-Ecosystem/aihub-be/issues/412), [#560](https://github.com/AiHub-Ecosystem/aihub-be/issues/560)
- Related ADRs: [ADR-0103](0103-budget-postgresql-connections-on-shared-cluster.md)

## Context

Read-only inspection on 2026-10-15 and 2026-10-16 found the monitoring stack on `69.62.74.196` and the AIHUB application/shared PostgreSQL host on `76.13.218.96`. The live stack runs Prometheus `v3.13.4`, Grafana `12.4.11`, Tempo `2.10.8`, and Alertmanager `v0.34.1`. The existing Prometheus target API listed Alertmanager and the three bot jobs only, with no AIHUB targets. Prometheus has no host-published port; Grafana and Alertmanager are bound to loopback. The running stack files are untracked in a heavily modified, separate IELTS-writing worktree. To keep its source and unrelated services untouched, the AIHUB overlay runs a separate Prometheus `v3.13.4` on the existing private `monitoring` network and sends alerts to the existing Alertmanager. Its UI binds only to `127.0.0.1:9094`; the existing Prometheus, Grafana and Alertmanager are not recreated.

On the AIHUB host, `aihub-db` publishes PostgreSQL only on `127.0.0.1:5433`. The full relevant `dashboard_backend` source audit found no Prometheus route or collector. Its separate Discord checks query application usage logs for error rate, request spikes, latency, and daily cost; those are application-level alerts, not host or dependency metrics. The read-only `s3-vps-watchdog` source checks SeaweedFS filer/S3/public-object health and `s3.wispace.app` TLS every 60 seconds, and exposes only loopback `/healthz` on port 9909. It exports no metrics. Blackbox probes add certificate-expiry samples for all five AIHUB/asset hostnames so each expiry has a Prometheus alertable series. On the monitoring host, Redis is authenticated, reports `maxmemory=256 MiB`, and uses AOF persistence. A dedicated ACL user is used for aggregate INFO metrics; it cannot read keys or Redis configuration.

A monitoring-host resource snapshot on 2026-10-15 showed 7.8 GiB total memory, 1.9 GiB available, no swap, and 63% root-disk use. Prometheus, Grafana, Tempo, and Alertmanager used about 395 MiB combined at the instant sampled. On 2026-10-16, Redis required authentication, reported `maxmemory=256 MiB`, and used about 2.4 MiB. Redis persistence has AOF enabled. Its exporter will use a dedicated ACL user that can read aggregate INFO metrics and cannot read keys or Redis configuration.

External TLS handshakes on 2026-10-16 succeeded for `api.aihubproduction.com` (expiry 2026-11-28), `sandbox.aihubproduction.com` (2026-12-15), `aihubproduction.com` and `www.aihubproduction.com` (2026-11-27), and `s3.wispace.app` (2026-11-14). The nginx alias `aihub-api.aihubproduction.com` had no public DNS record. Other hostnames on the shared VPS are not classified as AIHUB services and need owner review before they enter the probe set. Both hosts reported NTP synchronized; the sampled Production chrony offset was about 0.13 ms and the monitoring host's timesync offset was about -20 ms. These are snapshots, not continuous Prometheus signals.

The prior #474 blocker, #456, is closed. On 2026-10-16 the AIHUB owner confirmed authority over the shared hosts, PostgreSQL and Redis, and approved the scoped collectors and resource ceilings. The overlay caps additional memory/CPU at 384 MiB/0.45 CPU on Production and 512 MiB/0.70 CPU on the monitoring host. Prometheus has 14-day and 512 MiB TSDB retention settings; the size setting limits blocks, not WAL/filesystem use. These are configuration budgets; actual use still needs measurement. Existing cross-service notification agreements (#362), the broader alert catalog (#412), and the independent #237 application metrics/tracing work remain tracked separately. ADR-0103 records an 80% cluster connection alert threshold and the owner-approved 20-connection monitoring/operations headroom; other application allocations remain tracked by #560.

## Decision

Keep a versioned AIHUB monitoring bundle in this repository. Its images are pinned to node_exporter `v1.12.1`, `ghcr.io/google/cadvisor:v0.60.6`, postgres_exporter `v0.20.1`, Redis exporter `v1.93.0-alpine`, blackbox_exporter `v0.28.0`, and Prometheus `v3.13.4`. Review image security updates before upgrading them.

Exporters bind to an operator-selected, non-public host address. The AIHUB Prometheus service reaches monitoring-host exporters through the observed Docker bridge gateway `172.27.0.1`. It reaches Production exporters through SSH local forwards to their loopback listeners; the forwards bind only to that gateway and the SSH key permits only the three approved destination ports. The existing monitoring network remains unchanged. No exporter is published on a public interface; Prometheus binds only to `127.0.0.1:9094`, with operator access through an SSH local forward.

Keep cAdvisor behind the explicit `container-metrics` Compose profile. The AIHUB owner approved this collector scope on 2026-10-16. The Docker socket mounted read-only still grants root-equivalent Docker API access; Prometheus retains only cAdvisor series whose container name begins with `/aihub`. cAdvisor does not retain stopped-container history, so its OOM and restart alerts cover observed running-container series only.

Use a separate PostgreSQL monitoring credential file and one dedicated `aihub_monitoring` login. The login can execute only a fixed `SECURITY DEFINER` function owned by `aihub_admin`; it returns aggregate cluster connection/lock counts and sizes/transaction durations for `aihub` and `aihub_sandbox`, without SQL text or per-role labels. Do not grant `pg_monitor` or `pg_read_all_stats`. The pinned postgres_exporter `v0.20.1` custom-query extension is deprecated upstream; keep the image pinned and replace that query path before upgrading past supported compatibility. Keep `pg_stat_statements` disabled until the shared-cluster restart, per-AIHUB-database extension, normalized-query privacy check, and queryid/database-only export have been coordinated with all affected owners.

Keep PostgreSQL, Redis and SSH credentials in owner-only host secret files rendered from Vault; Compose contains file paths, not values. Run secret-reading exporters and the SSH tunnel as the matching unprivileged host account. The observed Redis limit is 256 MiB, so the rule uses 80% of that value. Recheck the fixed threshold if Redis `maxmemory` changes. Redis configuration collection remains disabled.

Version alert expressions with their metric sources and catalog entries. The current Alertmanager route sends `warning` to `discord-warning` and `critical` to `discord-critical`, Pushover, and Telegram. Rules cover disk above 80%, memory below 10%, container OOM/restart, PostgreSQL connections at 80% of `max_connections`, Redis memory above 80% of its observed 256 MiB bound, Redis mean command latency above 100 ms, certificate expiry within 14 days or failed probes, and unavailable targets. Alert severity and non-issue-defined thresholds remain proposals for the #412 policy review; the owner approved collector/resource scope, not a blanket paging policy. The Redis threshold must be revisited if `maxmemory` changes.

## Consequences

The repository contains an AIHUB-owned Compose overlay, scrape configuration, alert rules, a PostgreSQL aggregate function, and runbooks/catalog rows. The existing monitoring repository and its live Prometheus configuration are left untouched. The overlay's loopback Prometheus UI is accessible through SSH forwarding; Grafana datasource provisioning remains outside #474. CI validates Compose syntax and Prometheus configuration/rule syntax. Those checks do not establish target reachability, metric coverage, alert delivery, resource fit, or production state.

Keep #474 open until every required target is `UP` with expected samples, outside port probes show no exporter is public, hourly certificate probes are producing samples, scoped alert rows are recorded in the #412 catalog, PostgreSQL/Redis access boundaries are verified, and measured resource use fits the approved ceilings. See [the observability runbook](../operations/aihub-observability.md) and [the host/dependency alert catalog](../operations/alert-catalog.md).
