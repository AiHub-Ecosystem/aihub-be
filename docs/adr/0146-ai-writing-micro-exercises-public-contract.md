# ADR-0146: Serve AI Writing micro-exercises through Public API v2

- Status: Proposed — success captures and route-level handling are recorded; provider failure examples are written confirmations, not live HTTP captures. Provider timeout enforcement, prompt/output logging, and onward model-provider retention remain unverified.
- Date: 2026-11-02
- Amends: [ADR-0143](0143-public-v2-serves-ai-writing-v3-grading.md) decision 3, which promises that customers send `data_micro` back unchanged
- Related: [ADR-0100](0100-writing-task1-chart-image-uploads.md), [ADR-0127](0127-public-api-uri-major-versioning.md), [ADR-0129](0129-public-route-and-response-convention.md), [ADR-0140](0140-tenant-identity-is-the-organization-and-end-user-id-pair.md), [#1454](https://github.com/AiHub-Ecosystem/aihub-be/issues/1454)

## Context

Issue #1454 adds create-micro-exercise, create-longwriting-exercise, and grading-micro-exercise. The existing public `data_micro` object is trait → code → `{ prompt, question_type, comments[] }`; the provider instead asks AIHUB to select specific errors and supply other operation fields. The public request therefore needs an AIHUB-owned shape and mapping. Synthetic Production captures now cover all seven micro response types, long-writing creation, short- and long-writing grading, Task 1 image input, and two provider refusals. The provider supplied written examples for the non-400 errors and all three soft-fail fallbacks on [issue #1489](https://github.com/AiHub-Ecosystem/aihub-be/issues/1489); they are recorded as provider samples, not live captures. The team reports a current 60-second timeout ceiling on all three routes and plans to enforce 30/20/10 seconds. The existing AIHUB budgets of 45/35/20 seconds and nginx budgets of 55/45/30 seconds align only with that future target. The captured contract is recorded in [AI Writing exercise provider contract v2](../contracts/ai-services/ai-writing-exercises-v2.md). The AI Writing team has confirmed header precedence, exercise-data storage, telemetry retention, and Uvicorn log rotation in its written response on [issue #1454](https://github.com/AiHub-Ecosystem/aihub-be/issues/1454). Whether prompts or outputs appear in Uvicorn logs and onward model-provider retention remain unverified.

## Decision

- Add `POST /v2/ielts/writing/micro-exercises`, `POST /v2/ielts/writing/long-writing-exercises`, and `POST /v2/ielts/writing/micro-exercises/grade`, following ADR-0129.
- Give all three operations the `writing.exercise` scope and distinct metering operation names. Require `Idempotency-Key` for each. Successful response bodies are retained for replay for 24 hours in the existing idempotency store. The provider stores no exercise state, but AIHUB consequently retains generated exercises and answer keys, or grading scores and feedback, for that replay window; only a request fingerprint is stored for the request.
- A create-micro request selects one error entry from `data_micro`; create-longwriting selects two to four. Requests contain the needed topic, writing task, criterion, error code, prompt, question type, comments, and any supported image reference. Customers do not need to prove that they previously called grading. AIHUB validates its public request and maps it to the provider schema; it does not pass `data_micro` through as an opaque body.
- Expose the provider's seven micro exercise types on the micro route and `long_writing` through the long-writing route, after evidence exists for each exposed response shape. `exercise_type` may be omitted or null to let the provider choose a compatible micro type; the response identifies the result through `meta.type`.
- Map provider `504 gateway_timeout` to `AI_SERVICE_TIMEOUT`; leave `429 rate_limited` and `500 internal_error` to the dispatcher's status mapping, which returns `AI_SERVICE_THROTTLED` and `AI_SERVICE_ERROR`. Never forward provider error text, and preserve the provider's `Retry-After` header on throttling.
- Treat micro grading's integer score from 1 to 10 as a practice score, not an IELTS band score or verified result tied to a particular generated exercise. The provider returns no exercise identifier and is stateless. Client-graded exercise types include `correct` in the response; the customer application is responsible for keeping answer keys from learners until appropriate.
- Treat a provider HTTP 200 soft-fail response as a contract failure: create responses with zero questions/empty exercises and grading responses with score 0 are rejected by AIHUB's response schemas. They return `AI_SERVICE_CONTRACT_VIOLATION` and are not billed to customer quota; the provider says it absorbs the upstream model cost.
- AIHUB owns the public response schema and models exercise variants as a union discriminated by `meta.type`. Preserve exercise content and answer keys, and omit provider `usage`, `cost`, `metrics`, and `message` from the customer response, consistent with ADR-0143.
- Allow API keys with `writing.exercise` to use the existing authenticated Writing chart upload and completion flow for exercise images. Keep ADR-0100's image validation, public delivery, retention, and upload limits; AIHUB does not fetch arbitrary image URLs.
- Persisted-value compatibility (ADR-0128): `writing.exercise` is a new value in the API-key scope array. The reader stores scopes as a plain string array, so a previous release (N-1) does not reject a key that carries it. N-1 does not know the scope, so it answers `403` for an exercise-only key on the chart-upload routes and has no exercise routes. This release teaches the reader and allows issuing the scope together, which departs from ADR-0128's two-release rule. The AIHUB owner accepted this exception on 2026-11-02 during review of PR #1488; this ADR stays Proposed for the provider evidence below. Deploy as a coordinated cutover and do not issue exercise-only keys while N-1 still receives traffic. Customer Web does not offer the scope until the provider's non-400 failure behaviour is captured (#1489).
- Limit each public request body to 256 KiB and enforce provider field limits locally: topic 200 characters, prompt 2,000, quote/explanation 1,000, image URL 2,048, and user answer 1,500 for short writing or 4,000 for long writing. Use AIHUB timeouts of 45 seconds for micro creation, 35 seconds for long-writing creation, and 20 seconds for micro grading. Set nginx timeouts 10 seconds higher: 55, 45, and 30 seconds respectively. These budgets align with the provider's planned 30/20/10 second per-route limits; the provider currently reports a 60-second ceiling, so the current timeout hierarchy is not yet verified against deployed provider behavior.

## Evidence required before release

- The provider supplied scrubbed response examples for `429 rate_limited`, `500 internal_error`, `504 gateway_timeout`, and the three 200 soft-fail fallbacks in issue #1489. Obtain live failure captures before treating those examples as observed exchanges.
- Confirm that the provider has deployed and tested its planned per-route 30/20/10 second timeouts, then capture its own 504 through AIHUB's 45/35/20 second budgets. The current provider ceiling is 60 seconds, which exceeds AIHUB's operation budgets; AIHUB can time out before that provider timeout fires. The nginx 55/45/30 second budgets remain 10 seconds above AIHUB.
- Confirm whether request prompts or outputs appear in Uvicorn logs and how onward model providers retain or delete data. The AI Writing team reports no exercise, answer, or grading data stored in Postgres/S3, telemetry retained for 30–90 days with user-specific purge on request, and Uvicorn request-metadata logs rotated every 7–14 days; payload logging details remain unspecified.
- AIHUB's 24-hour idempotency replay retention is documented in the personal data inventory as a replay deadline, not a deletion guarantee.
- Keep provider compatibility between error-code and exercise-type combinations provider-owned. A captured `GRA02` + `reorder` request was refused with `400 invalid_request`; AIHUB returns `INVALID_REQUEST` and does not guess which combinations are supported.

The captured contract is pinned for implementation, while the open evidence above remains a release risk.
