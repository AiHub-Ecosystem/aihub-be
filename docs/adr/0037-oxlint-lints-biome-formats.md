# oxlint lints, Biome formats

Status: accepted

The repository splits static analysis between two tools. oxlint owns linting; Biome keeps formatting and `organizeImports` and has its linter switched off. A single tool would be simpler, and the split is the thing a future reader is most likely to question, so the reason is recorded here rather than left to be inferred from two config files that each look arbitrary alone.

Biome's linter was configured as `linter.rules.recommended` and nothing more. That set is genuinely small, and the gaps are not incidental: it has no import rules, no promise rules, no Node rules, and no Jest rules. For a Fastify gateway that fronts Postgres, Redis, and downstream HTTP, those are the four families whose absence is felt. oxlint supplies all four as native plugins and has no formatter, and Biome's formatter is the house style every file in the repository is already written in, so replacing the lint half and keeping the format half is the only combination that adds rules without a reformat. Consolidating on Biome's linter was rejected because it does not have the rules; consolidating on oxlint was rejected because it cannot format. Waiting for Biome to grow the rules was rejected because the wait has no date attached and [#110](https://github.com/AiHub-Ecosystem/aihub-be/issues/110) depends on oxlint specifically.

This is not a speed change and must not be sold as one. `biome check .` completes in under 300ms on 361 files; oxlint does not meaningfully beat that at this size, and a claim that it does is unsupported by any measurement taken here. What the change buys is rule coverage, and the honest accounting of that coverage is small: 23 findings, fixed in code. The larger reason to do it now is sequencing. oxlint's type-aware rules — `no-floating-promises` among them, the defect class this gateway is most exposed to — require `oxlint-tsgolint` and a TypeScript 7 compiler, neither of which is available. Installing and tuning oxlint against the syntax-only rules today means [#110](https://github.com/AiHub-Ecosystem/aihub-be/issues/110) becomes a flag flip and a findings backlog when TypeScript 7 lands, rather than a toolchain change and a compiler change arriving in the same diff.

Only the `correctness` category is enabled, plus `promise/always-return` and `import/no-named-as-default-member` named individually. Every other category was measured against this codebase before being left off, and the measurements are recorded in [the adoption comment on #106](https://github.com/AiHub-Ecosystem/aihub-be/issues/106#issuecomment-5770026510) rather than repeated here. The short form is that `style` reports 12,541 findings and `restriction` 4,716, both dominated by rules this codebase deliberately contradicts; `pedantic` reports 864, mostly `require-await` and function-length limits; and `suspicious` reports 69, of which two are real. Enabling `suspicious` as a category would have meant five suppression or option entries in exchange for those two findings — including switching off its largest rule — which is the configuration shape the originating issue warned against. Naming the two rules instead keeps the file a positive list: no category is disabled to make the run green, and there are no suppressions, no overrides, and no file-level ignores.

`unicorn/no-array-sort` is worth naming as a rejection because it looked like the most valuable rule in `suspicious` and is not. Its diagnostic text says `Array#sort()` mutates the original array, but the rule performs no mutation analysis and flags every `.sort()` call, including `[...xs].sort()` and a sort of a fresh array literal. All ten production call sites here sort an array built immediately beforehand, so the rule is entirely false-positive against this codebase. Its suggested fix is also unavailable: `toSorted()` requires `lib: ES2023` and `tsconfig.json` is on `ES2022`. Bumping the library target repository-wide to satisfy a rule that catches nothing was rejected as the more expensive half of a trade with no upside.

The pinned version is `^1.83.0`, not the `1.84.0` the originating issue named. pnpm 11 enforces a minimum release age on new dependencies, and 1.84.0 was a day old when this landed; `pnpm add` resolved that by writing twenty `minimumReleaseAgeExclude` entries into `pnpm-workspace.yaml`, one per platform binary, which would have committed a standing exemption from a supply-chain guard in exchange for one minor version of a linter. 1.83.0 clears the age gate on its own, produces byte-identical findings against this codebase — all twenty-three, rule for rule — and leaves `pnpm-workspace.yaml` untouched. The issue's version was written as "at time of writing" rather than as a requirement, so this is a substitution rather than a deviation.

Severity is set to `error` inside `.oxlintrc.json` rather than passed as `--deny-warnings` on the `pnpm lint` command line. oxlint exits 0 on warnings, so without this the lint step reports findings and still passes. Putting it in the configuration means `pnpm lint` and `.husky/pre-commit` read the same severities and cannot drift apart, at the cost of a pre-commit hook that refuses a commit carrying an unfixable finding. That cost is already the hook's established shape: it runs `pnpm run type-check` and `pnpm run test` as well, so a lenient lint gate between two strict ones would have been the inconsistency.

`pnpm lint` is `oxlint . && biome check .`. With `linter.enabled` false, `biome check` still reports `organizeImports` and `format` diagnostics and still exits non-zero, so the formatting half of the gate needs no separate command and no `--check` flag. `.oxlintrc.json` carries comments, which is valid JSONC and which oxlint accepts, so Biome parses that one file with `json.parser.allowComments` through an override — the alternative, renaming it to `.oxlintrc.jsonc`, would have cost oxlint's automatic config discovery and forced an explicit `-c` on every invocation.

Formatting ownership shifts only for JSON. `prettier` had been handed `*.{json,md,yaml,yml}` in `.lintstagedrc` while `generate:openapi` ended with `biome format --write openapi.json`, so one committed file had two formatters competing for it. JSON moves to Biome and that conflict ends. Markdown and YAML stay with prettier because Biome 1.9.4 cannot format them, which leaves those extensions formatted only on staged files and verified nowhere — a pre-existing gap this decision does not close. Closing it means reformatting every file under `docs/` in one commit, which would have buried the linter change it travelled with, so it is filed as [#125](https://github.com/AiHub-Ecosystem/aihub-be/issues/125) instead of being folded in here.

CI is untouched. `pnpm verify` already calls `pnpm lint`, and the workflow already calls `pnpm verify`, so the new linter reaches CI without a workflow edit. Splitting those checks into parallel lanes is [#108](https://github.com/AiHub-Ecosystem/aihub-be/issues/108) and stays separate.
