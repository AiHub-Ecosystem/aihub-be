# Self-serve Organization creation boundary

Status: accepted

Date: 2026-09-22; related issue: [#133](https://github.com/AiHub-Ecosystem/aihub-be/issues/133). Supersedes the sentence in [ADR-0027](0027-organization-membership-and-key-management.md) that kept Organization creation and first-owner assignment operator-provisioned.

No shipped path created the first Organization Membership: `org:create` wrote only the `organizations` row, invitation needs an active owner or admin, and acceptance needs an invitation, so every new Organization was unreachable without a hand-written `INSERT`. An active AIHUB User Account may now create a Self-serve Organization through the Bearer boundary and becomes its first active `owner`. Creation, first-owner membership, and the `organization.created` Organization Audit Event commit in one transaction; an Organization with no owner is the state this decision exists to remove, so a partial result is never acceptable.

The request carries only a name (trimmed, 1–100 characters, not unique, because a global uniqueness check would let a caller probe which names other tenants use). Commercial terms are never caller-declared: a Self-serve Organization starts from configured defaults of entitlement `writing`, a monthly request quota of 100 with hard stop, 60 requests per minute, and 5 concurrent requests. These are deliberately tighter than the operator defaults because no commercial agreement exists yet, and changing them stays an operator act. The `writing` entitlement is what lets the owner create a usable API key immediately; the quota and hard stop cap what that key can cost.

Unlike every other Bearer mutation, this one has no Organization to scope a rate limit to, and cost accrues from Organizations that exist rather than from how fast they are made. The Organization Creation Limit is therefore a configured lifetime count of 3 creations per account, not a time window. It is counted from a new nullable `organizations.created_by_user_account_id` column (null for operator-provisioned Organizations) rather than from audit events, because audit events are pruned after 24 months and the allowance must not quietly regrow. Suspension or ownership transfer does not return an allowance. The count and insert run after locking the caller's `user_accounts` row, the same row-lock serialization ADR-0029 uses, so concurrent requests cannot both pass the check. Exceeding the limit returns `409 ORGANIZATION_CREATION_LIMIT_REACHED` — not `429`, since waiting never helps — and writes no audit event, because no Organization exists to own it.

Idempotency reuses the single durable seam from ADR-0038 under a new Account Idempotency Scope (account, mutation type, key): `idempotency_records.organization_id` becomes nullable, and because a primary key cannot hold a null column the key becomes a `UNIQUE NULLS NOT DISTINCT` constraint over the same four columns, so a null Organization is one value rather than none and every Organization-scoped key behaves as before. `Idempotency-Key` is optional, as on invitation create; a completed replay returns the original Organization and spends no allowance, even after the limit is reached. The audit event uses `target_type` `organization`, the new Organization's id as target, its name as the redactable label, and no detail; the constraint extension follows migration 0012's drop-and-re-add shape. `actor_user_account_id` stays `NOT NULL` and ADR-0035's rejection of `actor_kind` still holds, because a real account acts. The limit is one global value; a per-account override is not built until an operator needs one.
