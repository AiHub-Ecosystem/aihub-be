# Organization suspension boundary

Status: accepted

Date: 2026-09-23; related issue: [#137](https://github.com/AiHub-Ecosystem/aihub-be/issues/137). Amends [ADR-0035](0035-organization-audit-trail-boundary.md) on who may stand as the actor of an operator act.

`organizations.status` is read on nearly every authorization decision, yet nothing could set it except a hand-written `UPDATE` against production. The one lever for stopping a non-paying or abusive tenant therefore had no record of who pulled it, and no trusted way back. Two operator commands now own it: `org:suspend --org <id> --actor <username>` and `org:restore --org <id> --actor <username>`. They live in `src/cli` as TypeScript beside the usage commands rather than as SQL in `scripts/cli/cli.mjs`, so the audit event is built by the same domain code every Bearer mutation uses. Neither act is reachable from the Bearer boundary: an owner who could suspend their Organization gains nothing, and one who could restore it would make suspension useless.

Suspension changes `status` and nothing else. API keys stay `active`, open invitations keep their own expiry, memberships and quota counters are untouched, and the Organization Creation Limit is not refunded. Restoration is therefore exact: it returns the Organization to the state it held before, with no side effect to undo. Both commands are state-idempotent — repeating an applied status succeeds and records nothing, as ADR-0029's membership repeats do.

Each command runs one transaction: it locks the Organization row `FOR UPDATE`, returns early when the status already matches, otherwise updates it and writes one `organization.suspended` or `organization.restored` event — `target_type` `organization`, the current name as the redactable label, empty `detail`. No reason is recorded. ADR-0035 rejected a `reason` column, tenant owners read `detail` through the Organization Audit Read, and redaction cannot reach it, so free text there would be an unredactable, tenant-visible note in an immutable table; an operator's ticket system holds the why. Each run mints one `req_<ULID>` as the event's originating request and prints it, so the operator can cite it and the audit contract is unchanged.

ADR-0035 kept `actor_user_account_id` `NOT NULL` and rejected an `actor_kind` column because operator acts had no code path. They now do, and the column stays `NOT NULL`: `--actor` names the operator's own AIHUB User Account, which must exist and be active or the command exits without writing anything. An `actor_kind` of `operator` with a nullable account was rejected. It reopens a recorded decision and changes the audit read contract, and it proves nothing more: anyone able to run the command already holds database credentials, so no mechanism here can authenticate the operator, and naming a real person is the most honest record available. The consequence is deliberate — the tenant's owners and admins see that username in their trail. Knowing who suspended you is transparency, not a leak, and operators should act from a dedicated staff account such as `aihub-ops-alice` rather than a personal customer one. If operator acts multiply until a staff account per act becomes a burden, the actor vocabulary is the one migration to revisit.

API-key authentication reads Organization status from the per-key identity cache, which holds a record for up to 60 seconds. After committing, each command purges the cache entry of every key the Organization owns, so the next request is decided against the new status; restoration purges too, so a restored tenant is not refused for another minute. A purge failure does not undo the committed act. The command says separately that the status changed and the cache was not purged, and the ceiling is the same 60 seconds `key:revoke` already promises. Requests already past authentication run to completion and are metered normally; cancelling in-flight downstream work would need machinery out of proportion to the case.

One operator path stays unaudited and is out of scope: `org:create` in `scripts/cli/cli.mjs` still writes without an Organization Audit Event. `key:create` and `key:revoke` are audited since #148: each requires `--actor`, and each records `api_key.created` or `api_key.revoked` with the same `detail` whitelist as its Bearer counterpart, in the same transaction as the key change. `key:revoke` deliberately differs from the Bearer path in one way: it works for an Organization in any status, because an operator revoking a leaked credential must be able to do so for a suspended Organization.
