# Organization API-key self-service creation boundary

Status: accepted; customer Environment set amended by ADR-0056

## Amendment for #182 (ADR-0056)

Customer key creation may issue a separate key restricted to `sandbox`. Customer sandbox keys are for Writing Task 1 and Task 2 and are not combined with production credentials; the existing default remains `{production}`. The production/staging-only restriction below records the original boundary and is superseded for sandbox-key creation by ADR-0056.

An authorized member creates an organization API key with `POST /v1/organizations/:organizationId/api-keys`, Bearer-authenticated and authorized against the durable membership resolved for the explicit `organizationId`; owners and admins may create keys and members may not. The request carries a name, requested scopes, optional allowed environments defaulting to `{production}`, and an optional expiry. The response is `201` with `Cache-Control: no-store` and returns the raw credential once as `data.api_key` alongside the same metadata shape the key-listing endpoint returns: `id`, `name`, `key_prefix`, `scopes`, `allowed_environments`, `status`, `expires_at`, `last_used_at`, and `created_at`. Key identifiers are `ak_` plus a ULID and are constrained by pattern in the public contract. The raw credential field is named `api_key` so that it matches the existing centralized redaction key set, which makes the "never logged" requirement a property of the mechanism rather than of discipline alone.

Requested scopes must belong to the distinct `requiredScope` set owned by the operation catalog; an unknown scope is a `400 INVALID_REQUEST` because the caller can correct it from the published contract, while a scope whose entitlement the organization does not hold is a `403 FORBIDDEN` because no request the caller can construct will succeed. Silently accepting a scope the organization cannot use, which is what the authentication-time `effectiveScopes` filter would otherwise do, is rejected: it produces a key that appears to carry access it does not have. That filter remains as defense in depth for entitlements withdrawn after creation. Allowed environments are restricted to `production` and `staging` by an application-layer list rather than a new organization column, because `sandbox` and `development` are not customer tiers and the existing `api_keys` shape is deliberately unchanged in this slice; a per-organization environment column remains the upgrade path if a customer requirement ever demands one. Expiry must be in the future and is capped at 365 days, so the existing `expires_at` column is enforced rather than decorative.

Creation locks the organization row with `SELECT ... FOR UPDATE` inside one transaction, re-reads organization status, counts active keys, and inserts. The lock is required for the cap of 50 active keys per organization to hold under concurrent creation, and it closes the window between membership resolution and insert in which an organization could be suspended, at no additional query cost. Exceeding the cap is a `403 FORBIDDEN`. The cap is enforced in the transaction rather than by a database constraint because this slice adds no schema change. Key creation goes through a management port separate from the authentication repository port, so the request hot path does not acquire management dependencies. The raw-credential format, hashing, prefix derivation, and identifier generation move into the identity domain and become the single source of truth; the operator CLI consumes them from the built output, following the existing precedent of a script importing from `dist`.

Creation deliberately carries no idempotency record. This conflicts with the user story that grouped create with invite and rotation, and follows ADR-0027, which scoped the idempotency seam to invite and rotation only. The seam's execution input is typed to the metered operation catalog, so admitting a control-plane operation is a change across the catalog, quota, and metering boundaries rather than a property of one endpoint; a creation retry that times out is recoverable by creating another key and revoking the orphan, which the key-listing endpoint makes visible. If a customer requirement later forces idempotent creation, widening the operation identifier is a prerequisite issue, not an amendment to this one. The identity cache is not purged on creation, because a negative cache entry for a freshly generated 256-bit credential is not a reachable state; cache purging remains the concern of revocation and rotation.
