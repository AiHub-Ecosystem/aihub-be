# Organization API key revocation boundary

Status: accepted

Revocation withdraws one credential and keeps its row. One Bearer-authenticated request names the key; owners and admins may revoke, members may not, and a suspended Organization is denied as for every other key mutation. The request carries no body, and the response returns the withdrawn key's metadata in the shared shape, which makes this the only place the published `revoked` status is ever reachable — listing deliberately omits revoked keys, and creation and rotation only ever return active ones. An unknown key and a key belonging to another Organization are both reported as not found, deliberately indistinguishable, as they are for rotation.

Revocation is state-idempotent. Revoking an already-revoked key succeeds and leaves `revoked_at` untouched, rather than failing as the originating issue's criteria asked. This follows ADR-0029, where the sibling membership operations are state-idempotent for the same reason: the goal of the request is that the key can no longer be used, and a second request finds that goal already met. Revocation is what someone runs while handling a leak, often twice, often from a script retrying after a timeout; answering the second attempt with an error turns an achieved outcome into something to investigate at the worst moment. This is the one place revocation and rotation deliberately differ on the same input: rotating a revoked key is a meaningless request, because there is nothing live to replace, while revoking one is a request that has already been satisfied.

An expired key can be revoked. Rotation refuses one because the replacement would inherit an elapsed expiry, which is a consequence of what rotation builds rather than a principle that dead keys are untouchable. Revocation builds nothing and only closes the record. Refusing would also trap an Organization: the active-key cap counts rows whose durable status is active, and an expired key still holds that status, so expired keys occupy cap slots. An Organization unable to revoke them could be held at its cap entirely by keys that no longer work.

There is no last-key invariant. An Organization holding no keys is a valid and ordinary state — every Organization starts there, and self-service creation exists to leave it — and an owner or admin can create another at any time through their Bearer session. That is what separates it from the zero-owner invariant, which guards a state nobody can escape because only an owner can appoint one. Refusing to revoke a final key would also refuse it exactly when the Organization's only credential has leaked.

The durable change is one transaction that locks the Organization row and then the key row, the order creation and rotation already use so that key mutations cannot deadlock against each other. The key-row lock is not protecting against concurrent revocation, which is harmless: two revocations agree. It exists for revocation racing rotation on the same key, where an unlocked read would take the pre-rotation row and return metadata describing a state that no longer holds by the time the caller sees it. This reason is recorded because a future reader who notices that revocation is idempotent would otherwise be right to conclude the lock is redundant.

The identity cache is purged for the key on every request, including the idempotent one that changes nothing. Purge failure is swallowed, as elsewhere, so a first revocation can leave the cache still admitting the key for up to roughly a minute with nobody informed. Purging again on a repeat request is what makes retrying a useful remedy for that: an operator who suspects the key is still working can run the same command and close the window, rather than reaching a no-op that leaves it open. `revoked_at` stays out of the published contract; it is durable state the criteria require, but it would be null in every other response that carries this shape, and when revocation happened is a question for the durable audit follow-up rather than a field on a read path.
