# Admit Organization-owned Sandbox keys to public grading demos

- Status: Accepted
- Date: 2026-10-13
- Related: [AiHub-Frontend #68](https://github.com/AiHub-Ecosystem/AiHub-Frontend/issues/68), [FE PR #67](https://github.com/AiHub-Ecosystem/AiHub-Frontend/pull/67), [BE PR #602](https://github.com/AiHub-Ecosystem/aihub-be/pull/602)
- Amends: [ADR-0056](0056-customer-sandbox-test-tier.md) for public-demo key admission and the allowed Sandbox grading scopes; Sandbox quotas and host isolation remain unchanged
- Extended by: [ADR-0095](0095-demo-environments-and-sandbox-allowance-policy.md), which accepts explicit demo environment selection and a revised Sandbox allowance; implemented by issue [#617](https://github.com/AiHub-Ecosystem/aihub-be/issues/617)

The public Writing and Speaking demos accept an optional Organization-owned API key that is restricted to the Sandbox Environment and carries `writing.grade`, `speaking.grade`, or both. This lets one temporary key serve both demo pages while keeping its environment and capability set narrow. `POST /v1/sandbox/demo/api-keys/validate` authenticates the key and checks the selected skill's scope without entering the grading dispatch or monthly quota path. This result is advisory to the browser: each actual grading endpoint authenticates the key again and runs its normal authorization, identity, rate-limit, and quota chain, so skipping or forging the first step cannot authorize grading. Sandbox key records remain uncached for request-time revocation and Organization-suspension enforcement.

The key identifies its Organization and that Organization remains the owner of usage and quota; AIHUB Web Session identity is neither substituted for the key nor used to bind a different Organization. When no active Identity Configuration exists, the demo supplies one random UUID as the temporary Declared User ID for a visit, shared across both skills rather than an AIHUB username, avoiding cross-tenant identity attribution. For an Organization with active Identity Configuration, successful non-dispatching key validation reports `user_identity_mode: signed_assertion`; otherwise it reports `declared_id`. The mode is returned only after the key, selected Environment, and required scope pass, and it exposes no identity configuration details. This signal only selects the frontend input: every actual identity-scoped upload or grading request still re-reads the Organization policy and verifies the supplied assertion independently. The existing `/v1/sandbox/assertions` signer remains dedicated to AIHUB's demo Organization. Customer API-key creation may issue Sandbox keys with only the Writing and/or Speaking grading scopes; it cannot combine Sandbox with another environment or add other scopes. Operators may provision equivalent demo keys through the documented `key:create` procedure.

## Amendment for issue #687 (2026-10-15)

This amends the original exclusion of Organizations with active Identity Configuration only at the advisory demo key-validation step. The signal uses persisted `active` status and does not probe JWKS reachability. If reading active identity configuration fails, validation fails closed with a retryable `503`; it must never fall back to `declared_id`. Sandbox and Production validation follow the same identity-mode rule, with their existing environment, key binding, scope, allowance, quota, and billing policies unchanged. Actual uploads and grading continue to require a valid Signed User Assertion for an active configuration; Declared User ID is not an authorization fallback.

This keeps anonymous exploration available without spending real grading quota or charging AIHUB's own demo Organization, while valid customer-owned keys still reach real Sandbox grading under the existing monthly, rate, and concurrency ceilings. Letting the browser's first validation authorize later submissions would be bypassable and would remain stale after revocation; making validation reserve a grading unit would charge before any answer was graded. Both alternatives are rejected.
