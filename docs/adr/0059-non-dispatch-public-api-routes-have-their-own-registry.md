# ADR-0059: Non-dispatch Public API Routes are declared in their own registry

- Status: Accepted
- Related issue: #173
- Related: [ADR-0057](0057-graded-request-order-is-a-declared-contract.md), [ADR-0038](0038-bearer-management-idempotency-scope.md)

The Organization-scoped management routes kept their public contract in three places at once: a path literal in the route declaration, a hand-written path constant in the OpenAPI builder, and a hand-written list of the statuses that operation could return. Issue #173 asked for all of them to read one list. We built that list, then did not put it in the Operation Catalog. A Control-plane operation authenticates with a Bearer User Access JWT, carries no API-key Scope, resolves no User Identity, and dispatches nothing to an AI Service, so it has no downstream service, no downstream path, no downstream contract, and no metering mode to declare. `OperationId` is the dispatch vocabulary: `http-operation-dispatcher.ts` hardcodes one `dispatch()` overload per operation id, and the first downstream, scope, and metering guards all resolve an id against the catalog and read those fields. Widening `OperationId` with non-dispatch ids would force one overload per route that never reaches a dispatcher, and would leave every catalog consumer reading a field those entries do not have. So the two registries are separate by construction, the way the graded-request set is declared separately from the Operation Catalog for the same reason (ADR-0057). The Public API Route registry owns each route's path, method, caller authentication, how the route learns its Organization, success status, idempotency mode, request and response schemas, and error statuses; route declarations and the OpenAPI document read from it, and the Postman handover collection follows from the document. It covers every Public API Route that does not dispatch: the eighteen Organization routes, the eight local auth routes, the sandbox assertion mint, and the unauthenticated Speaking question list. Together the two registries partition the Public API Routes rather than duplicating them, and `app.module.spec.ts` proves the partition is complete by comparing the registered routes against the generated document. Parameter descriptions, response prose, query parameter shapes, and the `x-identity-scope` extension stay with the builder's per-route path items, because a non-dispatch route's public difference from another is mostly exactly that prose. `x-identity-scope` later moved into the registry as `publishedIdentityScope`; the prose stayed.

## Considered options

One universal registry covering every Public API Route was rejected for the reason above, not for its size. A single flat entry with optional fields was rejected because the fields that would become optional are the ones every consumer reads: `downstream` is read by the metering service and the usage-completeness report, and `requiredScope` by the API-key guard and by `publishedScopes()`, which feeds API-key creation validation and the CLI's `--entitlement` list. Making them optional would push the check to each call site instead of the type. Reusing `identityScope: 'organization'` for the management routes was rejected: in the published document the field already carries four different values, because the four dispatch operations report `user` with an `X-User-Identity` parameter, eighteen management routes report `user` with `BearerAuth` and no such parameter, the auth routes report `none`, the sandbox assertion route reports `organization`, and the Speaking question list reports nothing. The field names the User Identity form an operation consumes, which no non-dispatch route does, so the honest move was to record what the document publishes rather than what the route resolves. The registry therefore carries `publishedIdentityScope`, named for the fact it states, and the builder derives `x-identity-scope` from it. Gathering twenty scattered literals into one declared field does not decide whether the values are right; it makes them visible enough to decide later, which is where a follow-up should start. Storing the OpenAPI path in the registry alongside the Nest path was rejected in favour of deriving it, because two spellings of one route is the drift this ADR exists to remove; `toOpenApiPath` converts `:organizationId` to `{organization_id}` in one place. Declaring `maxBodyBytes` and `timeoutMs` was rejected: the body-limit and timeout hooks key on an exact path, so a `:segment` path is silently never matched, and a declared limit that is never applied is worse than no declaration. Two guard tests now hold that line. This does not drop the word "limits" from either issue's definition of the catalog; that sentence describes the dispatch catalog, whose limits bound a proxied request to an AI Service. Neither issue's acceptance criteria list a limit among the fields a non-dispatch operation must declare, and a non-dispatch route's request body is bounded by the framework's own ceiling, so there is no limit for the entry to record. Recording a number the hooks ignore would satisfy the wording and break the guarantee. Declaring the `security` entry was accepted and applied only where it was already duplicated across call sites — the eight auth routes and the two singleton routes — while the eighteen management routes keep one identical `BearerAuth` line each, because rewriting eighteen uniform lines buys nothing and each rewrite is a chance to publish a different document.

## Consequences

The builder keeps one path item function per non-dispatch path, so a new non-dispatch route is still a hand-written function; what the registry removes is the second and third copy of its path and its status list. The generated document is byte-identical to the one published before this change, including the `Idempotent-Replay` descriptions, which stay route-specific and are passed to the generator rather than declared once. `errorStatuses` accepts a literal list or `'all-except-idempotency-conflict'`, which the sandbox assertion mint uses because it reports a `409` it can never reach; a literal list is the preferred form everywhere else, because it is the only one that fails when a new error code appears. `auth.verify_email` publishes a `204` alongside its registered `200`, and `auth.refresh` publishes a bespoke `401` that is not the shared error component — both stay in the path item, because the registry records a route's primary success status, not every status it can answer. Non-dispatch routes deliberately carry no `maxBodyBytes` and no `timeoutMs`, so a request to one is bounded only by Fastify's own ceiling; if a route ever needs a tighter bound, the hooks need pattern matching first, which is a separate decision. The `identityScope` comment in the Operation Catalog no longer promises an `'organization'` value, and `scripts/check-architecture.mjs`'s `timeoutMs` count rule still expects exactly the four dispatch entries because no other route declares one.
