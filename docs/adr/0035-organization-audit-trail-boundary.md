# Organization audit trail boundary

Status: accepted

Organization control-plane mutations become durable evidence. One append-only table, `organization_audit_events`, records membership, invitation, and API-key changes for every Organization, closing the audit deferral [ADR-0027](0027-organization-membership-and-key-management.md) declared. Membership, invitations, and keys share one table because they share one shape — actor, Organization, target, action, outcome, request correlation, moment — and because the question the trail exists to answer is "what happened in this Organization", which across three tables is a union rather than a query. The difference between the domains lives in `target_type` and `detail`, which is where a difference that narrow belongs.

The audit write shares the mutation's transaction, and a failed write fails the mutation. Repositories own transactions here and the application layer has no unit-of-work seam, so the event is assembled inside the repository that already opens the transaction. It is assembled there rather than handed down because most of what an event says is only knowable under the locks: the target's durable identifier, the role it held before the change, the metadata a key carried. The application contributes what it alone knows — the acting account — which the API-key ports now name explicitly beside the organization they already carry. An outbox was rejected because audit lives in the same Postgres as the rows it observes, so the worker, the sink, and the delivery window would all be machinery bought for a hop that does not happen. Best-effort emission after commit was rejected outright: it fails exactly where the trail matters most, leaving a revoked key with no record of who revoked it. A unit-of-work abstraction threaded through every repository to serve one table was rejected as a larger change than the feature.

Denials are recorded, and they cannot share that transaction. Both refusals are reached inside it — the authority decision runs under the organization and membership locks, where the target's current role is first known, and the zero-owner conflict is counted under those same locks — and both then roll the transaction back, so an event written there would vanish with the rollback it was meant to outlive. Denial events therefore commit on their own, and a failure returns the original denial with a log line instead of escalating to an internal error. The asymmetry against the mutation path is deliberate and is the thing a future reader is most likely to mistake for an inconsistency: a committed mutation with no trace loses evidence that state changed, while an unrecorded denial loses a signal about a change that never happened. Making audit availability a precondition for answering `403` would let an audit outage become an authorization outage, which is a worse failure than the one it would prevent.

What is not recorded is as decided as what is. A state-idempotent repeat writes nothing, because [ADR-0029](0029-organization-membership-mutation-boundary.md) made repeating an applied state succeed, and a trail that records deliveries rather than acts is diluted by exactly the retry behaviour that boundary encourages. An idempotency replay writes nothing for the same reason, and `idempotency_records` already holds the original request correlation for anyone who needs to reach it. A denial from a caller holding no active membership in the named Organization writes nothing, because recording it would hand any authenticated account a write into another tenant's history by guessing an `organizationId` — a cross-tenant write primitive built out of an audit feature. An unknown-target denial writes nothing even when the caller does belong to the Organization: the boundary answers identically for a target that does not exist and a target belonging to another tenant, and recording the attempt would record precisely what that answer withholds. The consequence is that `target_id` is `NOT NULL` and every `denied` event names a real target.

`target_id` is polymorphic and carries no foreign key, pointing at a membership, an invitation, or a key as `target_type` says. Three nullable typed columns with real keys would buy referential integrity at the price of a coalesce in every read, and `ON DELETE RESTRICT` from the audit table would give the record a veto over the lifecycle of what it records — the observer blocking the observed. `organization_id` and `actor_user_account_id` are monomorphic and keep their restricting keys, which costs nothing in a schema that deletes no rows physically. Beside `target_id` sits `target_label`, the identifier as it read at that moment: a username, a normalized email, a key name. It is denormalized deliberately, because a trail that resolves labels when it is read narrates the past using present-day names, which is the one thing an audit trail must not do.

`actor_user_account_id` is `NOT NULL` and there is no `actor_kind`. Every mutation in scope crosses the Bearer boundary with a real AIHUB User Account behind it; operator-provisioned Organization creation and first-owner assignment have no code path in this repository, and `src/cli` holds only usage and quota maintenance. A column enumerating `operator` and `system` would be constraint values for code that does not exist, and the `NOT NULL` it would give up is a real invariant available for free today. The same reasoning removed a `reason` column: no boundary accepts one, the originating issue's required fields do not include it, and a permanently null column is a field every future reader must learn to ignore. Both are recorded rejections rather than omissions, and both are one migration away when the code that needs them arrives.

The action set enumerates only shipped mutations, constrained by the database rather than left as free text, so that a typo cannot become a permanent action name in a table nobody can edit. Invitation revocation was deferred when this boundary was first accepted; it now ships as `invitation.revoked` under [ADR-0036](0036-organization-invitation-revocation-boundary.md), with its constraint extension in migration 0012. A member disabling their own membership is not a distinct action either; it is `membership.disabled` where actor and target coincide, which the data already says. Ownership transfer writes one `membership.owner_transferred` event carrying both parties, not two role changes: [ADR-0029](0029-organization-membership-mutation-boundary.md) established transfer as an atomic command rather than a promote/demote sequence, and splitting it in the audit would contradict that ADR, invent a self-demotion nobody performed, and force a reader to join two rows to learn who holds ownership.

No secret enters the trail. `detail` is populated from a per-action whitelist in code — the before and after of what changed, a key prefix where a key is involved, and on a refusal the reason it was refused — rather than by serialising an input object, because serialising an input is exactly how a raw credential reaches a table that cannot be edited afterwards. A refused attempt carries no after-state: an event saying a role became `member` would describe a change that never happened, so it names what was asked for and leaves the transition out. Raw API keys, invite tokens, passwords, signed User Assertions, and raw request and downstream bodies are excluded as they are everywhere else. `key_hash` and `token_hash` are excluded too, which goes beyond what the originating issue asked: a hash of a short-lived token is an offline-guessable verifier, and `key_prefix` already tells a human which key an event concerns.

Immutability is enforced by a `BEFORE UPDATE OR DELETE` trigger. Deletes are refused unconditionally, updates are refused for every column but `target_label`, and that column may only be emptied: permitting a new value would turn the single writable column into a way to restate history. A dedicated database role with `REVOKE UPDATE, DELETE` is the stronger control and was rejected because this repository defines no roles or grants at all, so adopting one to protect a single table opens an operational surface out of proportion to the gain; convention alone was rejected because it is an intention, not a guarantee. The one writable column is Audit redaction, the only sanctioned modification, and it exists because invitation events record the normalized email in plaintext. Hashing it would remove no category of personal data from a system that already stores the same address in plaintext in `organization_invitations` and `user_accounts`, while making the trail unreadable to the people who must read it. What the trail changes is that address's lifetime, so an erasure request nulls the label and leaves the row, its actor, its action, and its timing standing. Redaction is named in `CONTEXT.md` rather than left as an implementation detail: a reader who believes this table is absolutely immutable believes something false.

Retention is 24 months, against the 13 months [ADR-0023](0023-thirteen-month-usage-retention.md) gives metering. Usage records expire because settled billing data stops mattering; audit evidence expiring means the evidence is gone at the moment a dispute produces the need for it. Indefinite retention was rejected as a promise with no way back, which collides with the erasure obligation redaction exists to serve. At control-plane volume — thousands of rows a month rather than one per request — 24 months costs nothing. Read access belongs to active owners and admins of the named Organization and is scoped to it. The read endpoint now ships; [ADR-0040](0040-organization-audit-read-boundary.md) records its keyset order on `(occurred_at DESC, id DESC)` and its cursor. The `oae_` identifier is minted by the module-level monotonic factory in `organization-audit-event.store.ts`, so IDs generated for one `occurred_at` within a process sort in mint order. This guarantee is process-local: separate instances can mint IDs in the same millisecond without a defined relative order. The read query and cursor still include both columns, so their correctness does not depend on ID chronology. The existing btree on `(organization_id, occurred_at DESC)` supports the read; no schema sort column was added. The prune command remains a scheduled gap. The BRIN index that earns its place on `usage_records` does so at per-request volume and would be an optimisation for a query nobody has written.

The append-only guarantee is proven in the `test:db` lane against a real database, because a migration spec asserting that a file contains `CREATE TRIGGER` is evidence about a string, not about whether an `UPDATE` is refused. That lane is not part of `pnpm verify` and stays that way: adding it would make a running PostgreSQL a precondition for every verification run in the repository, which is a change to the development contract for everyone and a decision separate from this table. The migration keeps a string-asserting spec in the fast lane as the other tables do, which holds the schema's intent visible in `verify` without pretending to prove the trigger.
