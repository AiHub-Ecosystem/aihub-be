# Organization API key list boundary

Status: accepted

The organization API-key view is a Bearer-authenticated, organization-scoped read available only to active owners and admins; a suspended Organization is denied, matching the open-invitation listing rather than the caller-scoped self-roster, because both are organization-scoped management lists behind the same authority while the roster is a different shape. The response carries unpaginated key metadata in the shared shape the creation endpoint already returns—identifier, name, display prefix, scopes, allowed environments, status, expiry, last-used time, and creation time—never the credential hash or any raw credential, in deterministic newest-first order by creation time with the identifier as tie-break. An Organization with no keys receives an empty list rather than an error.

Only keys whose durable status is active are listed. Revoked rows stay durable and unlisted: the question this view answers is which credentials are live, and revocation history belongs to the durable audit follow-up. Leaving revoked rows out is also what keeps the response bounded, because the fifty-key cap applies to active keys alone; the absence of pagination here is therefore a consequence of that cap rather than an independent judgement, and raising the cap or listing revoked rows reopens pagination.

Published status is `active`, `expired`, or `revoked`, widening the two-value union the creation endpoint published in the previous slice. `expired` is derived at read time from the key's expiry moment by one pure function in the identity domain, not stored and not recomputed in SQL: the rule already exists in the authenticator, and a second copy in SQL would additionally decide it against the database's clock rather than the application's. The authenticator's own expiry check is left alone; it is a rejection guard on the request path, not a projection. A creation response can never carry `expired`, since a requested expiry must be in the future, and the published contract says so rather than leaving a reader to infer it. Listed `last-used` time is approximate by design: the authenticator's touch is throttled to one minute and issued fire-and-forget, so the value can lag or be missing, and the contract describes it as approximate instead of implying precision.

Widening an enum in a response contract that has already been published is a breaking change for a strict consumer. It is accepted here because the creation endpoint shipped hours earlier with no release and no generated clients, and because the alternative—a second key-metadata schema for listing—would duplicate the shape that slice existed to define once, leaving four endpoints to describe one key in two ways. The same widening would not be acceptable once an integrator has generated a client from the published contract.

Listing adds no lock, transaction, pagination, filtering, query parameters, or cache-control header. No `no-store` header is set: the response carries no credential, and reserving that header for responses that do keeps it meaningful. Tenant scoping lives entirely in one `WHERE` clause, which no substituted repository can prove, so the database lane covers tenant isolation, the active-only filter, and ordering against the real engine.
