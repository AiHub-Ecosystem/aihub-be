# ADR-0056: Customer API-key sandbox test tier

- Status: Accepted
- Date: 2026-09-27
- Related issue: [aihub-be #182](https://github.com/AiHub-Ecosystem/aihub-be/issues/182)
- Related issue: [AiHub-Frontend #27](https://github.com/AiHub-Ecosystem/AiHub-Frontend/issues/27)
- Amends: ADR-0017, ADR-0018, ADR-0030

AIHUB provides a free-to-customer test tier at `sandbox.aihubproduction.com` for customer Organizations. An owner or admin can issue a separate API key restricted to `sandbox`; customer sandbox keys can grade Writing Task 1 and Task 2. The calls use the real AI Writing service, so the allowance is finite and is a request-count ceiling, not a USD-denominated cost guarantee. The existing demo Organization and its server-held Sandbox API key retain their Speaking flow.

Organization, API-key, and identity-configuration records have one durable source in the production control-plane database. The sandbox application reads the required Organization, key, and identity fields through a least-privilege connection, with only the narrow `last_used_at` update needed by authentication. It does not cache successful key lookups, so key revocation and Organization suspension take effect on the next request. The existing demo Organization, identity configuration, and key record move back to the production control plane; preserving its key hash and identifier keeps the BFF's raw key valid. The sandbox database continues to own sandbox usage, idempotency state, and quota reservations. Production and sandbox usage and quota state remain independent. The sandbox connection fails closed when the control-plane database cannot be read.

The sandbox runtime receives a read-only control-plane URL from its Vault connection bundle. Its database role can read only the Organization fields needed for admission, the API-key fields needed for authentication, and the Organization identity fields needed for signed assertions; it can update only `api_keys.last_used_at`. Control-plane writes continue through the production runtime. Sandbox usage, idempotency, and dispatch reservations use the sandbox `DATABASE_URL`.

Each customer Organization receives at most 25 sandbox AI dispatches per UTC calendar month. The entire sandbox environment, including the existing demo Organization, receives at most 500 AI dispatches per UTC calendar month. The shared limit can be exhausted before one Organization uses all of its individual allowance; at either ceiling AIHUB returns `429 QUOTA_EXCEEDED` until the next UTC month. During normal operation, Redis-backed burst controls limit traffic to five requests per minute per API key, one in-flight grading request per Organization, and ten in-flight grading requests across the sandbox environment. These pacing controls follow the existing degraded-mode policy; the durable monthly reservation is the hard spending boundary. The demo Organization keeps its configured per-Organization quota as an additional limit.

The sandbox application reserves one dispatch atomically in durable sandbox Postgres after validation and completed-idempotency lookup, immediately before calling a downstream AI service. A request that reaches the dispatch boundary consumes a unit even if the downstream call later fails or times out. A request known not to have reached that boundary releases its reservation. Admission fails closed if the reservation store cannot verify either ceiling. A completed Writing idempotency replay returns its stored result without a new reservation or AI call, even after either quota is exhausted; this is a sandbox exception to ADR-0018's quota-before-idempotency order. An in-flight duplicate keeps the existing idempotency conflict behavior.

The sandbox Environment is customer-accessible but remains hostname-bound. Customer keys use the customer's Organization Identity Configuration and never use `/v1/sandbox/assertions`; that minting route remains restricted to the configured demo Organization. The sandbox key and its Customer Web Sample request are tracked separately in AiHub-Frontend #27, which depends on backend #182 and frontend #23.

This decision supersedes ADR-0017's placement of sandbox Organization, key, and identity-configuration rows exclusively in `aihub_sandbox`, while retaining the separate sandbox application, usage database, Redis logical database `/1`, hostname, and downstream runtime realm. It extends ADR-0030's customer key environments to include a sandbox-only key. It amends ADR-0018 only for sandbox dispatch budgets and completed replays; production quota behavior remains unchanged.

The cutover was executed by a one-off, dry-run-first `pnpm migrate:sandbox-control-plane -- --org <org_id>` command. Applying it copied the Organization, all API keys, and identity configuration to the production control plane, narrowed the moved keys to the `sandbox` environment while preserving key IDs and hashes, then removed only those control-plane rows from Sandbox. Historical usage and idempotency remained in Sandbox; current-month Sandbox dispatches were copied into durable reservations so the shared and configured demo allowances continued across cutover. Pre-feature downstream-error records without reservation evidence were conservatively counted because their dispatch status cannot be reconstructed, and the dry run reported the count. It refused to move organizations with membership, invitation, or audit dependencies.

That command ran once, and it is now removed together with the earlier #50 procedure; both are retained as a record in [Customer Sandbox control-plane cutover procedures](../history/customer-sandbox-control-plane-cutover.md), and git history retains the tool. The layout they produced is the runtime contract above, not a procedure to re-run.
