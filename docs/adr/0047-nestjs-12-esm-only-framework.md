# ADR-0047: NestJS 12, an ESM-only framework loaded from CommonJS

- Status: Accepted
- Related issue: #138

The application moves to NestJS 12 so that the Fastify serving requests carries the fixes for both open Fastify advisories. The NestJS 11 Fastify adapter pins Fastify exactly at 5.11.3, and even its newest 11.x release keeps that pin, while every NestJS 12 adapter pins a patched 5.12.x. A package-manager override forcing a patched Fastify under the NestJS 11 adapter was the smaller change and was rejected: it would run the adapter on a Fastify minor its maintainers had not paired with it, and it could never be retired, because the 11.x line was never going to catch up. Upgrading lets the adapter choose its own Fastify, and one direct Fastify dependency at the same version keeps exactly one copy in the tree. A resolution spec (`test/fastify-resolution.spec.ts`) fails the build if the adapter and the application ever load different copies again, or an unpatched one.

NestJS 12 packages are ESM-only. The application stays CommonJS, built by SWC, and loads them through Node's `require()` of ESM, which is unflagged only from Node 22.12 on the 22 line. Building needs more: the NestJS 12 CLI behind `nest build` loads its schematics tooling, which requires an ESM dependency inside a require cycle, and Node 22.14 rejects that with `ERR_REQUIRE_CYCLE_MODULE`; NestJS documents 22.22.3 as the CLI's floor. The repository both builds and runs, so its declared engine floor is 22.22.3, and the container image moved from 22.14.0 to 22.23.2 for both its build and runtime stages, the version CI and the upgrade spike already ran. This replaces the scaffold plan's choice of CommonJS as a way to run without any ESM compatibility layer: `require()` of ESM is now that layer, provided by Node itself. This is the first time the application's runtime has depended on it, so an older Node fails at build or startup rather than with an obvious version error, and the engine field is what turns that into a warning at install time.

Jest's module loader does not implement `require()` of ESM, so both Jest lanes stop excluding the NestJS packages from transformation and let the existing SWC transform compile them to CommonJS. Moving to Jest 30 or Vitest, or migrating the application itself to ESM, were each larger decisions than this upgrade needed and remain open. The release chosen is the newest NestJS 12 that has cleared the package manager's minimum release age; no exclusion was added to reach a fresher one.

The same change clears the development-only dependency alerts with overrides scoped to the vulnerable range, each commented with the package that forces it. Two are major jumps forced by `postman-collection`, which pins `uuid` 8.3.2 and `@faker-js/faker` 5.5.3 exactly. `uuid` 11 is kept: the committed Postman collection regenerates identically apart from the random ids that library mints on every run. `faker` 10 is not: it removed an API `postman-collection` loads, and generation fails. That alert (GHSA-qxc2-j82w-r537) is dismissed instead, because it needs untrusted input to `helpers.fake`, and the project only generates a Postman collection from its own OpenAPI document at build time; the dependency never reaches the production image.
