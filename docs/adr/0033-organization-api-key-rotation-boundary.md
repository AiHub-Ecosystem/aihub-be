# Organization API key rotation boundary

Status: accepted

Rotation replaces an Organization's credential while preserving the authority it carried. One Bearer-authenticated request names the key to replace; owners and admins may rotate, members may not, and a suspended Organization is denied as for every other key mutation. The replacement inherits the key's name, scopes, allowed environments, and expiry, because rotation changes the credential and not what the credential may do; changing the expiry would change the authority under cover of replacing the secret. The response is the shape creation already returns — the raw credential once, alongside the new key's metadata — so a caller installs a rotated key through the same model as a created one. The replacement is a new key with its own identifier: the caller's reference changes, and the identifier it supplied names only the key being retired.

A key that is already revoked, or whose expiry has passed, cannot be rotated and is refused as forbidden. Inheriting an elapsed expiry would otherwise mint a credential dead at birth, and the alternative of silently clearing the expiry would convert a deliberately time-boxed credential into a permanent one. Rotating a dead key has no use: creating a new one is the operation that was wanted. A key that does not exist and a key belonging to another Organization are both reported as not found, deliberately indistinguishable, so the endpoint cannot be used to discover which identifiers exist in another tenant.

Rotation is exempt from the active-key cap. It never changes how many active keys an Organization holds, and an Organization sitting at its cap must be able to replace a leaked credential — the moment rotation matters most is exactly the moment a naive cap check would refuse it. Stating the exemption is deliberate: ordering the transaction so the revoke precedes the count would produce the same result by accident, and the next person to reorder that transaction would silently remove a rule they did not know it carried.

The durable change is one transaction that locks the Organization row and then the key row, in that order, matching creation so that two concurrent key mutations cannot deadlock against each other. Locking the key row is what makes concurrent rotation safe: without it both callers read the key as active, both revoke it, and both insert, leaving the Organization with two live replacements where one was asked for and only one was ever installed — an unaccounted live credential, which is the outcome rotation exists to prevent. The loser of that race sees the key already revoked and is refused. Locking the Organization row keeps suspension effective when it lands between authorization and the write.

The old key's hash leaves the repository so the application can purge the identity cache for it. This is the first time a key hash crosses that boundary, and it is not a breach of the rule against logging or returning key hashes: the value moves between two layers in memory and reaches neither a log nor a response. Purge failure stays invisible, as the cache port already swallows it; the resulting cache ceiling of roughly sixty seconds is the operational risk ADR-0027 accepted, not a grace window, and surfacing a failure the request cannot act on would add a signal with no reader.

Rotation carries no idempotency record, which departs from ADR-0027's statement that invite and rotation reuse the existing idempotency seam. That seam persists the response body — `idempotency_records.response_body` is required once a record completes — so replaying a rotation means storing the raw credential durably, which is precisely what the one-time disclosure rule forbids. The departure costs little, because a retried rotation is self-correcting: the second attempt revokes the unacknowledged replacement, creates another, and returns a credential the caller can actually use, leaving behind only a revoked row that listing already omits. Protecting rotation against retries would require an idempotency mechanism that can replay a decision without replaying a secret, which is a different design than the one this codebase has.
