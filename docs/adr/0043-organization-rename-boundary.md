# Organization rename boundary

Status: accepted

Date: 2026-09-23; related issue: [#136](https://github.com/AiHub-Ecosystem/aihub-be/issues/136). Supersedes the sentence in [ADR-0035](0035-organization-audit-trail-boundary.md) that makes `target_label` the only column Audit redaction may change.

An Organization's name was fixed at provisioning, and no path could correct it. It is the only attribute of an Organization that carries no authority, costs nothing, and bounds nothing. An active owner may now change it through `PATCH /v1/organizations/:organizationId`, whose body is `{ name }` with extra properties rejected, so a client that sends a quota or an entitlement is refused rather than silently ignored. Entitlements, rate limit, concurrency, monthly request quota, hard stop, and status stay operator-controlled: an owner who could raise their own quota would be making a billing change dressed as a rename.

Only an active owner of an active Organization may rename. Admins, members, non-members, disabled callers, and suspended Organizations receive one `403` with one message, following the audit read: a distinguishable refusal would let a caller with no membership learn which guessed Organization exists or is suspended. Suspension is refused, unlike the audit read, because a rename is a management mutation and suspension closes management surfaces; a tenant rebranding mid-investigation would muddy exactly the record an operator is examining. The authority decision, the previous-name read, the update, and the audit write run in one transaction under `FOR UPDATE` locks on the Organization and caller membership rows, as [ADR-0029](0029-organization-membership-mutation-boundary.md) does, so an owner demoted by a concurrent transfer cannot rename.

The name is validated by the one rule self-serve creation applies — trimmed, then 1–100 characters, not unique — extracted so both paths share it. The operator `org:create` CLI applies no such rule, so a stored name can be padded or longer than 100 characters; this is a known conflict, not corrected here. Equality is exact and case-sensitive after trimming the request, with no Unicode normalization: `Acme` to `ACME` is a rename, because case fixes are the typo correction this boundary exists for. Renaming to the current name succeeds and records nothing, matching ADR-0029's state-idempotent repeats; that also makes the [ADR-0038](0038-bearer-management-idempotency-scope.md) idempotency seam unnecessary, so no `Idempotency-Key` is accepted. No rate limit is added: only owners can rename and every rename is audited.

A rename records one `organization.renamed` event with `target_type` `organization`, the new name as `target_label`, and `detail: { previousName }`, because a trail that only says a rename happened cannot answer what the Organization used to be called. An attempt by an active admin or member records a `denied` event per ADR-0035, with the current name as label and `detail: { denial: 'insufficient_authority' }`; the requested name is omitted, since it is free text from a caller without authority, written into a table nobody can edit. Suspended and non-member refusals record nothing, as elsewhere.

`organization.created` made the name redactable, which admits that a name can be personal data — a sole trader's business is often their own name. Leaving `previousName` in `detail`, which the append-only trigger forbids changing, would quietly make that redaction incomplete. The trigger therefore also permits a `detail` change on exactly one shape: `OLD.action = 'organization.renamed'`, `NEW.detail = OLD.detail - 'previousName'`, and `NEW.target_label IS NULL` in the same update. Redaction stays one act that removes both names together; no new value can be written, and no other action's `detail` becomes writable. Separate redaction of the previous name was rejected because two partial acts on one event are harder to reason about than one complete one.
