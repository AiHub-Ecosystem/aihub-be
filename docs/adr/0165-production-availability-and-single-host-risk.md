# ADR-0165: Production availability and single-host risk

- Status: Accepted
- Date: 2026-11-14
- Amends: ADR-0011
- Related: #657, #281, #298, #327, #362, #364, #372, #386, #400, #454, #560, #588, #642, #740, #875

## Context

AIHUB Production runs on one shared VPS. The application, host nginx, and shared PostgreSQL cluster occupy that Production host; PostgreSQL is outside the AIHUB Compose project, not outside the host ([ADR-0104](0104-observe-shared-host-and-dependency-health.md), [#298](https://github.com/AiHub-Ecosystem/aihub-be/issues/298)). The service owner confirms Redis runs on a separate VPS, making it a distinct failure domain. A read-only check on 2026-11-14 found the monitored Redis instance up, with zero connected replicas, AOF enabled, and successful AOF/BGSAVE status. `INFO replication` required authentication; no credential was read or used. The exporter target was not independently tied to the service endpoint, and these metrics do not rule out a proxy or service-level failover. The live AOF setting also differs from the Redis spec, which calls for 15-minute RDB snapshots and AOF disabled; the latest RDB save time was not available. Vault and SeaweedFS remain separately operated single-instance dependencies. The current internal Production SLO is 99.5% for the four critical journeys, with an error-budget policy; it is not a customer SLA ([SLO policy](../operations/slo.md)).

PostgreSQL backups run hourly to Cloudflare R2, encrypted with a key held off-host. The documented PostgreSQL RPO is about one hour. A read-only Production check at 2026-11-14 15:02 UTC found successful uploads for both databases at 14:47 UTC, about 15 minutes earlier. Issue #281 records successful restore rehearsals, most recently on 2026-10-18, and a measured 5–9 second database restore at the current small data volume; that is not a clean-host recovery time. The next rehearsal is due 2026-11-18. Issue #454 owns the still-unrehearsed Production/Sandbox host rebuild. The location of the R2 data is not recorded in the repository.

## Decision

- Accept the current single-host Production topology as an MVP risk. Do not add high availability or replicas under #657.
- Keep the existing 99.5% internal Production SLO and error-budget policy. Do not publish an uptime SLA. Sandbox remains outside the SLO and follows the existing best-effort availability posture.
- Set the PostgreSQL RPO target to no more than one hour for both Production and Sandbox databases and all durable records in them, including usage/billing evidence and idempotency records. This accepts the possibility of losing up to one hour of those records after a restore. Redis counters remain rebuildable from durable usage records. The hourly off-host backup and restore process is owned and evidenced by #281; current backup freshness is an operational check, not an availability commitment.
- Do not claim a numeric RTO for total Production-host loss. Recovery remains best-effort until #454 completes a clean-host rehearsal and records end-to-end recovery time. The 5–9 second PostgreSQL restore measured by #281 is only one component of that recovery.
- Accept the current singleton posture for the Production host, nginx, PostgreSQL, Redis, Vault, and SeaweedFS; do not add redundancy under #657. Redis is on a separate Wispace VPS; the 2026-11-14 observation supports a single monitored instance without connected replicas, while upstream failover and recovery remain unverified. Its AOF setting differs from the current Redis spec and its latest RDB save time was not verified.

- Require an HA re-evaluation and plan before accepting a customer contract whose availability requirement exceeds the single-host posture; when the PostgreSQL RPO target is missed or the future host-loss RTO target is missed; or when measured demand reaches the approved Production capacity budget. A trigger requires a decision and plan; it does not automatically deploy HA. Do not use a fixed RPS/concurrency trigger until #560 and production-representative capacity evidence establish one.
- Defer cross-region recovery. Revisit it when a customer contract or a confirmed data-residency requirement calls for it. Continue the existing off-host backups, but record their permitted location only after the storage region is verified with the owners of #740 and #875.
- Do not run multiple application hosts until cross-host lease, expiry, and clock behavior is designed and verified. This includes the Email Outbox claim and failure-report leases and other time-based claim predicates: use the database clock or define and test a maximum clock-skew bound. Declare a maximum replica count, then bound #372's per-process fallback limits and #560's database connection budgets for that overlap. The mechanism is deferred; the Raft proposal in a #657 comment is not adopted by this ADR.
- Provider-diversity choices (including AI, email, and payment providers), broad external-vendor inventory, and operator staffing are outside this decision and remain with their existing owners.

## Consequences

Loss of the Production host can interrupt the gateway and shared PostgreSQL until manual recovery. Restoring PostgreSQL may lose up to one hour of durable records, and full-host recovery has no numeric time commitment until rehearsed. The existing single-host choice is deliberate for the MVP, with the triggers above as its exit conditions.

This ADR supersedes the fixed multi-node trigger of 300 RPS or 1,000 concurrent connections in deployment-roadmap §N.5: those figures are not an approved Production capacity budget. The section now defers the numeric trigger until #560 and representative capacity evidence provide one. Other §N.5 triggers are unchanged.

The #657 references to #16 and #400 as the host-isolation and backup-restore owners are inaccurate: #16 concerns idempotency, #298 owns shared-host database isolation, #281 owns off-host PostgreSQL backups and restore rehearsals, and #400 owns pre-deploy migration rehearsal on a restored database. #372 owns degraded-mode behavior, while #588/#642 cover in-process bulkheads. Full-host rebuild is #454.
