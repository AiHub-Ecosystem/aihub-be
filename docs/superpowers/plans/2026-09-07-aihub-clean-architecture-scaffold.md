# AIHUB Clean Architecture & Agent Workflow Scaffold Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:executing-plans` (or `superpowers:subagent-driven-development` when explicitly selected) to implement this plan task-by-task.

> **Status: executed. Kept as a record of what the scaffold set out to do.**
>
> One constraint below has since been lifted: the plan deliberately left the Writing grading response parser unimplemented while the downstream contract was unknown. That contract was resolved on 2026-09-07 by calling the live service, the responses are committed under `test/fixtures/ai-writing/`, and the parser now exists. Read the constraint as the reasoning of the time, not as current guidance.

**Goal:** Turn the docs-only AIHUB repository into the smallest runnable NestJS/Fastify modular-monolith scaffold with a Casso-inspired Clean Architecture layout, enforceable boundaries, and Claude Code/Matt workflow guidance.

**Architecture:** One deployable NestJS application. Business modules use `presentation -> application -> domain`; infrastructure implements application ports and may depend inward. `domain` has no framework or I/O imports. Cross-cutting primitives live in `src/common`; the operation catalog and boundary contracts live in `src/catalog` and `src/contracts`; downstream adapters are pure request/response mapping seams and never perform I/O.

**Tech Stack:** Node.js 22 LTS, pnpm, TypeScript strict mode, NestJS 11, Fastify, TypeBox, Jest, Biome, and `dependency-cruiser`. `undici`, `jose`, Drizzle/Postgres, Redis, ULID, and Opossum are added only with the first feature that actually needs each one.

## Global constraints

- Treat `src/contracts/` and `src/catalog/` as the executable public API source. Use `docs/superpowers/specs/2026-09-07-aihub/01-context-and-stack.md` through `11-open-questions.md` for runtime decisions; consult `docs/history/aihub-deliverable-1-historical-contract.md` for original D1 rationale only.
- Preserve the existing docs-first structure; do not duplicate the full specifications in `CONTEXT.md`, `CLAUDE.md`, or ADRs.
- Keep the repository a single application. Do not create a monorepo, frontend, Speaking/Reading modules, a dedicated proxy, a billing subsystem, dynamic routing, object storage, or an async job system in this scaffold.
- Never put API keys, signed assertions, internal tokens, essay content, or raw downstream bodies in logs or error messages.
- Tenant identity is explicit (`organizationId` in context and application inputs); domain code must not read request headers, environment variables, Redis, Postgres, or downstream HTTP clients.
- Redis is a cache/counter/protection dependency only; durable usage, idempotency, and control-plane truth belong to Postgres when those modules are implemented.
- Keep the first scaffold contract-safe: no Writing response parser is implemented until the unknown grading response fixture is resolved.
- Every task ends with the smallest relevant verification command and one focused commit.

- Initialize the package as `aihub-be` with a `0.1.0` version and Node 22 engine. Use CommonJS output for the first Nest scaffold so decorators, Jest, and the Nest CLI work without an ESM compatibility layer.
- Install only the packages required by this scaffold: `@nestjs/common`, `@nestjs/core`, `@nestjs/platform-fastify`, `fastify`, `reflect-metadata`, `rxjs`, and `@sinclair/typebox`.
- Install development packages: `@nestjs/testing`, `@types/jest`, `@types/node`, `@biomejs/biome`, `dependency-cruiser`, `jest`, `ts-jest`, and `typescript`. Add `undici`, `jose`, Drizzle/Postgres, Redis, ULID, and Opossum with the first implementation task that uses them.

- Configure Biome for 2-space indentation, single quotes, trailing commas, and the repository’s TypeScript files. Ignore external AI-writing JSON fixtures under `test/fixtures`; do not rewrite user-provided test data. Do not introduce ESLint and Prettier alongside Biome.
- Implement `src/main.ts` with `NestFactory.create` using `FastifyAdapter`, a global `/v1` prefix, and a JSON body limit matching the 1 MiB public request limit from the implementation spec. Keep production hardening (proxy trust, CORS, rate limits) in later tasks where the policy is defined.
- Implement `src/app.module.ts` with only `HealthController` registered. The health controller returns a stable `{ status: 'ok' }` response and has one unit test; it is not a business endpoint.
- Add `.gitignore` entries for `node_modules`, `dist`, `coverage`, `.env`, `.env.*`, `.claude/settings.local.json`, and OS/editor files. Never ignore tracked specification files.
- Keep pnpm's build allowlist minimal in `pnpm-workspace.yaml`; approve only `@biomejs/biome` because its executable needs the postinstall step.

**Verification**

## Task 3: Add the framework-neutral common foundation

**Files to create**

- `src/common/errors/error-code.ts`
- `src/common/errors/app-error.ts`
- `src/common/errors/error-envelope.ts`
- `src/common/errors/http-exception.filter.ts`
- `src/common/request-context/request-context.ts`
- `src/common/request-context/request-context.factory.ts`
- `src/common/security/redact.ts`
- `src/common/errors/app-error.spec.ts`
- `src/common/request-context/request-context.factory.spec.ts`
- `src/common/security/redact.spec.ts`

**Steps**

- Define the public error-code union from implementation spec section 07, including validation, authentication, authorization, not-found, conflict, rate-limit, quota, downstream, timeout, dependency, and internal categories. Keep the initial list typed and stable; do not add a second error taxonomy in individual modules.
- Define `AppError` with `code`, `message`, `httpStatus`, `retryable`, optional `details`, and a safe `cause` reference that is never serialized. The constructor must require an explicit public-safe message and preserve the original cause only for server-side logging.
- Define the response envelope `{ error: { code, message, request_id, details? } }` and a Fastify/Nest exception filter that maps `AppError` and unknown errors to it. Unknown errors return `INTERNAL_ERROR` without exposing stack traces or downstream bodies.
- Define `RequestContext` as the transport-independent request metadata passed through application ports:

  ```ts
  export interface RequestContext {
    readonly requestId: string;
    readonly receivedAt: Date;
    readonly deadlineAt: Date;
    readonly organizationId?: string;
    readonly apiKeyId?: string;
    readonly userId?: string;
    readonly scopes: readonly string[];
    readonly signal: AbortSignal;
  }
  ```

- `request-context.factory.ts` accepts already-validated boundary values and creates the context with a bounded deadline. It must not read headers or environment variables itself; presentation/auth code supplies those values.
- Implement `redact.ts` as a small pure helper that masks sensitive string fields (`api_key`, `authorization`, `user_assertion`, `internal_token`, `essay`, and `body`) before structured logging. Add tests proving the original object is not mutated and sensitive values are not returned.
- Keep all files free of Nest/TypeBox/database imports except the HTTP exception filter, which is explicitly presentation-facing infrastructure under the common boundary.

**Verification**

Run `pnpm test -- app-error.spec.ts request-context.factory.spec.ts redact.spec.ts` and `pnpm type-check`.

**Steps**

- Keep identity and gateway modules as composition seams only. Export ports, context types, and domain-safe values; do not implement API-key hashing, JWT verification, Postgres, Redis, or HTTP clients in this task.
- Define the identity ports around validated values and `RequestContext`, not `FastifyRequest` or raw headers. The API-key port returns organization/key metadata; the assertion port returns a verified user identity and scopes.
- Define the gateway dispatcher port around `OperationId`, typed input, and `RequestContext`. It must not expose an `undici` request, Fastify reply, or raw downstream response to callers.
- Define `DownstreamAdapter<TInput, TOutput>` with pure `buildRequest(input, context)` and `parseResponse(raw)` methods, plus a typed `DownstreamRequest` containing only method, path, body, and content type. Dispatcher/HTTP infrastructure owns headers, tokens, timeout, cancellation, and host selection. Adapter code must not choose hosts, read env, or call a client.
- Implement only `task1-grade-request.adapter.ts` as a pure fixture-backed request mapper. It maps the Task1 public input to the current downstream path and body, forwards only the context values required by the internal contract, and strips public-only fields that are not sent downstream. It must not implement grading response parsing because the source response shape is unresolved.
- Define `writing-grader.port.ts` as the application port future use cases will consume. It accepts a typed Task1/Task2 command plus `RequestContext`; it does not mention the concrete adapter or HTTP client.
- Register the three modules in `src/app.module.ts` without adding real providers. Empty speculative Speaking/Reading modules are explicitly not created.
- Add the adapter test for exact path/body mapping, no secret leakage in the generated headers/body, and no mutation of input/context. Use a plain object fixture; do not call a real service.
