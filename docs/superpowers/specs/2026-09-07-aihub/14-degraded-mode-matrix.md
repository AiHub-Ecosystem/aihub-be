# 14 — Dependency Degraded-Mode Matrix

← [Table of Contents](README.md) · [13 — Quota Reconciliation](13-quota-reconciliation.md)

This is the normative cross-dependency contract for down, slow, and wrong
dependency behavior. A **dependency seam** is one logical consumer or policy
boundary using a dependency. A dependency may therefore have multiple rows when
its consumers degrade differently. Only applicable failure modes get rows;
do not invent Cartesian `N/A` cases or downstream response shapes.

Each row records current behavior and the target contract, the client response
and retry semantics, the bounded signal, the lifetime of any last-known-good
state, and its rationale and proof owner. An accepted ADR wins over an older
spec or issue comment. Linked owner issues record implementation gaps; this
matrix does not duplicate their retry algorithms or alter a published response
contract on its own.

## Operating bounds

- The current single-host blue-green rollout can have two application slots
  serving together (`N = 2`). Process-local fallback and bulkhead totals can
  therefore reach twice their per-process limit. Adding application hosts
  requires a new replica cap and revised fallback/database budgets first
  ([ADR-0165](../../../adr/0165-production-availability-and-single-host-risk.md)).
- `/ready` is readiness for core grading: PostgreSQL or Redis probe failure
  returns `503`. `/health` is the static liveness response. Vault, object
  storage, email, AI Services, and customer JWKS are feature-level dependencies
  and do not make every instance globally unready.
- Provider work uses the operation's bounded deadline and explicit replay
  policy. Retryable client responses do not mean every operation is safe to
  replay; follow the linked idempotency/reconciliation contract.

Redis is one dependency shared by several guards. A slow command can stall
siblings until their bounded command timeout; #642 owns the isolation work.
The matrix records each consumer's outcome separately and does not treat
connection isolation as a new fallback policy.

## Readiness and recovery proof

PostgreSQL and Redis startup/outage/recovery are tested through the fault proxy
without restarting the app or container. `/ready` is `503` while either core
probe is unhealthy and returns `200` after same-process recovery within a bound
recorded by [#2019](https://github.com/AiHub-Ecosystem/aihub-be/issues/2019). `/health` remains static `200`. A dependency
whose failure is feature-scoped leaves `/ready` up and reports failure through
its row's operation error and signal.

DNS/IP cutover is also a same-process recovery contract: the old endpoint may
remain reachable or become black-holed, but after cutover new connections must
reach the new endpoint without an application restart. #749 owns PostgreSQL
connection rotation and #645 owns Redis late-command/replay behavior; they set
the numeric recovery bounds that #2019 verifies. The matrix does not
promise a DNS TTL bound that current code has not established.
