# API versioning and backward compatibility in production APIs

Research date: 2026-10-28

This note compares public guidance and product documentation from Google, Stripe, GitHub, and Microsoft. The providers use different version selectors and support windows; the recurring operating principles matter more than copying one provider's URL format or timeline.

## What major API providers do

| Provider        | Version selection and evolution                                                                                                                                                                                                                                                                                                          | Coexistence, migration, and retirement                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Google APIs     | The standard API Improvement Proposals use a major version such as `/v1`; compatible additions are generally made in place, while incompatible changes require a new major. Google distinguishes source, wire, and semantic compatibility and warns that visible behavior can break clients even when the JSON schema appears unchanged. | Different majors should work in the same client during a reasonable, communicated transition period. AIP-185 requires a reasonable deprecation period before shutdown. Google Enterprise APIs make a stronger, explicitly scoped commitment: at least one year's notice and no removal while customers are actively using a feature, except for security, legal, or similar exceptions. ([AIP-180](https://google.aip.dev/180), [AIP-185](https://google.aip.dev/185), [Google Enterprise API stability tenets](https://cloud.google.com/blog/topics/inside-google-cloud/new-api-stability-tenets-govern-google-enterprise-apis)) |
| Stripe          | Breaking changes arrive in named major API releases; monthly releases in that major are backward-compatible. The API version is also pinned by SDK releases, and webhook event schemas use the version configured for that endpoint (or the account default), so webhook consumers need their own migration step.                        | Stripe recommends testing against a new version before upgrading. Its upgrade guidance includes updating the SDK/request version, upgrading webhook endpoints, testing, then applying the change in Workbench; one published changelog describes a 72-hour rollback window for that upgrade. ([Versioning](https://docs.stripe.com/api/versioning), [upgrade example](https://docs.stripe.com/changelog/acacia/2024-11-20/link-card-brand))                                                                                                                                                                                       |
| GitHub REST API | Requests select a dated contract with `X-GitHub-Api-Version`. Breaking changes are released in a new version; additive changes, including response fields, are included in supported versions.                                                                                                                                           | GitHub supports an old version for at least 24 months after a new version is released. It publishes breaking-change guidance, sends `Deprecation` and `Sunset` headers as retirement approaches, and returns `410 Gone` when a retired version is requested. ([API versions](https://docs.github.com/en/rest/about-the-rest-api/api-versions), [breaking changes and upgrade guidance](https://docs.github.com/en/rest/about-the-rest-api/breaking-changes))                                                                                                                                                                      |
| Microsoft       | Microsoft Graph uses `/v1.0` for production and `/beta` for preview. Its producer guidelines recommend adding new API elements incrementally and versioning elements if a breaking change cannot be avoided.                                                                                                                             | Microsoft's Graph support page gives a 24-month retirement window for a deprecated API version or GA API. Separately, its producer guidelines require deprecated GA elements to remain supported for 36 months, or 24 months when non-usage is demonstrated. These commitments apply at different scopes (whole API version vs. individual elements). ([Graph versioning and support policy](https://learn.microsoft.com/en-us/graph/versioning-and-support), [Microsoft Graph producer guidelines](https://github.com/microsoft/api-guidelines/blob/vNext/graph/GuidelinesGraph.md))                                             |

Google's Ad Manager offers a concrete usage signal example: it publishes deprecation and sunset dates and lets customers receive an alert when calls are made to a deprecated API version. ([Ad Manager deprecation schedule](https://developers.google.com/ad-manager/api/deprecation))

## Common production principles

1. **Preserve the contract clients selected.** Keep compatible changes in the current major. A breaking change should have a new selectable contract, with the old one available during migration. Include behavioral semantics, errors, authentication, and enum evolution in the compatibility definition, not just field names and types. ([Google AIP-180](https://google.aip.dev/180), [Microsoft REST API Guidelines](https://github.com/microsoft/api-guidelines/blob/vNext/Guidelines.md))
2. **Make migration observable and actionable.** Publish a change list and migration guidance, test the target version, identify affected customers where possible, and announce deprecation separately from actual shutdown. A deprecation notice does not itself mean the old behavior has changed. ([GitHub breaking changes](https://docs.github.com/en/rest/about-the-rest-api/breaking-changes), [RFC 9745](https://www.rfc-editor.org/rfc/rfc9745.html))
3. **Measure consumers before retirement.** API gateways can attribute calls to a selected major and an authenticated customer/credential. Use recent and retained usage windows, last-seen time, and request counts to focus migration outreach. Treat unauthenticated or unidentifiable calls as unattributed, and avoid treating a short quiet period as proof that nobody depends on the API. The last sentence is an operational recommendation inferred from the need to demonstrate non-usage and account for migration. ([Microsoft Graph guidelines](https://github.com/microsoft/api-guidelines/blob/vNext/graph/GuidelinesGraph.md), [Google Ad Manager deprecation schedule](https://developers.google.com/ad-manager/api/deprecation))
4. **Keep deprecation and retirement dates distinct.** RFC 9745 defines `Deprecation` as the date the resource is or will be deprecated, encoded as a Structured Field Date. RFC 8594 defines `Sunset` as the expected unavailability date in HTTP-date format. The headers convey lifecycle information; a successor link can direct clients to migration details. ([RFC 9745](https://www.rfc-editor.org/rfc/rfc9745.html), [RFC 8594](https://www.rfc-editor.org/rfc/rfc8594.html))

The providers do not agree on one selector (`/v1`, a date header, an SDK-pinned version, or a query parameter) or one support period. Even one provider can set different timelines for a whole version and an individual element. Those are policy choices shaped by the product and customer base; compatibility guarantees, visible migration, and evidence before retirement recur across the examples.

## Application to AIHUB

AIHUB already has an accepted policy in [ADR-0127](../adr/0127-public-api-uri-major-versioning.md): use `/vN` as the only public major selector; keep compatible changes in the current major; create a new major only for a concrete breaking public contract change; serve supported majors concurrently; publish an immutable OpenAPI document and migration changelog per major; support the previous major for at least 12 months after its successor is released; review customer traffic and contact affected customers before sunset; then return `410 Gone` with the standard error envelope and successor information.

This is consistent with the major-version coexistence approach in Google's AIP-185 and the explicit old-version support in GitHub's API, while AIHUB's 12-month minimum is its own accepted product policy. GitHub's 24 months and Microsoft Graph's 36/24-month periods are comparison points, not reasons to silently change AIHUB's approved timeline.

For an upstream AI provider changing its response format, the useful boundary is the public contract: AIHUB can adapt the provider output internally and keep `/v1` stable. If AIHUB intentionally changes what customers receive in a breaking way, add `/v2` with that contract and run it alongside `/v1`; do not make `/v1` track the provider's schema automatically. This is an application of ADR-0127's contract/version boundary, not a claim that every provider API must use path-based versioning.

The relevant open implementation issues divide the lifecycle work:

- [#1362](https://github.com/AiHub-Ecosystem/aihub-be/issues/1362): emit RFC-correct deprecation and sunset dates separately, validate their order, and document/test the headers.
- [#1366](https://github.com/AiHub-Ecosystem/aihub-be/issues/1366): report public request totals by major and environment, and identify authenticated Organizations by request count and last-seen time. Organization-level details must remain in an access-controlled report, not Prometheus labels.
- [#1374](https://github.com/AiHub-Ecosystem/aihub-be/issues/1374): implement the first real `/v1` + `/v2` coexistence release after a concrete breaking public contract change is approved. It explicitly does not create a placeholder `/v2`.

These issues are complementary: #1374 serves multiple contracts, #1362 tells callers when the old contract is deprecated and sunsets, and #1366 provides evidence for the required pre-sunset customer review.
