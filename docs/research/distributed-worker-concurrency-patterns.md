# Concurrency protections for distributed async workers

Research date: 2026-10-29

## Distinctions that matter

These mechanisms protect different boundaries. A queue claim coordinates who starts; a compare-and-swap (CAS) protects a particular database transition; idempotency absorbs retries of the same logical operation; outbox/inbox patterns coordinate database state with message delivery; a lease supports failover; conditional publication prevents overwriting a selected result. None makes arbitrary external side effects execute exactly once.

For comparison, a fencing token is a monotonically increasing ownership generation that the protected destination checks on each write and rejects when older than the latest accepted generation. Merely issuing or carrying a token is not enough: the destination has to enforce it. Redis's distributed-lock guidance recommends fencing for long-running work, and Kubernetes client-go explicitly says its leader election does not guarantee fencing. ([Redis distributed locks](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/), [Kubernetes client-go leader election source](https://github.com/kubernetes/client-go/blob/master/tools/leaderelection/leaderelection.go))

## Patterns and their boundaries

| Pattern                                    | Useful for                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       | Limits compared with fencing                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Database CAS / optimistic concurrency**  | Atomically claim or complete a row only if its state/version still matches the expected value. A typical form is `UPDATE ... WHERE id = ? AND version = ? RETURNING ...`; zero affected rows means the expectation lost. This keeps the read/check/write decision in the database. ([EF Core concurrency guide](https://learn.microsoft.com/en-us/ef/core/saving/concurrency), [PostgreSQL UPDATE](https://www.postgresql.org/docs/current/sql-update.html), [PostgreSQL RETURNING](https://www.postgresql.org/docs/current/dml-returning.html)) | Protects only the database row and transition guarded by that predicate. It does not undo a network call already made by a stale worker. Broader multi-row invariants may need a short transaction at `SERIALIZABLE`; PostgreSQL requires retrying serialization failures (`40001`). ([PostgreSQL transaction isolation](https://www.postgresql.org/docs/current/transaction-iso.html))                                                                                                                                                                                      |
| **`FOR UPDATE SKIP LOCKED` queue claim**   | Lets competing database consumers claim different ready rows without waiting on each other's row locks; PostgreSQL calls this useful for queue-like tables. ([PostgreSQL SELECT](https://www.postgresql.org/docs/18/sql-select.html))                                                                                                                                                                                                                                                                                                            | `SKIP LOCKED` gives an intentionally inconsistent view and the row lock lasts only as long as its transaction. For long work, commit a durable claim/owner/version quickly; do not keep a DB transaction open while calling providers. A later timeout/reclaim can still leave the old process running, so it is not fencing.                                                                                                                                                                                                                                                |
| **Idempotency key + unique constraint**    | Makes a retry of the same logical action safe. Use a stable operation/message key and let a unique constraint or atomic insert choose one winner; store/return the prior outcome where the API contract needs repeatable responses. A check-then-insert in application code is race-prone. ([Microsoft idempotent consumer](https://learn.microsoft.com/en-us/azure/architecture/patterns/idempotent-consumer), [PostgreSQL unique constraints](https://www.postgresql.org/docs/current/ddl-constraints.html))                                   | Deduplicates the same key, not distinct work generations. It does not order different operations or prevent an older, differently keyed worker from overwriting newer state. Keep dedup records at least through the broker's redelivery/replay window; key independently by consumer when separate subscribers must each process a message. ([Microsoft idempotent consumer](https://learn.microsoft.com/en-us/azure/architecture/patterns/idempotent-consumer))                                                                                                            |
| **Transactional outbox / inbox**           | Outbox commits business state and an event row together, so a crash cannot commit one without recording the other. A relay publishes later. Inbox records a stable message key in the same local transaction as the consumer's database effects. ([AWS transactional outbox](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html), [Microsoft inbox/idempotent consumer](https://learn.microsoft.com/en-us/azure/architecture/patterns/idempotent-consumer))                                | Publication and delivery remain at-least-once in typical relays/brokers: consumers still need idempotency. Inbox atomicity covers only effects that join its transaction. For a third-party API or external store, use that destination's idempotency/CAS mechanism or reconcile in-progress outcomes; a local inbox cannot make a remote side effect atomic.                                                                                                                                                                                                                |
| **Lease with renewal/heartbeat**           | Provides temporary ownership and automatic failover after a process stops renewing. Kubernetes uses Lease objects for heartbeats and leader election; Redis describes renewal for work that may outlast a short TTL. ([Kubernetes Leases](https://kubernetes.io/docs/concepts/architecture/leases/), [Redis lock extension](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/))                                                                                                                                           | Expiry lets a successor proceed; it does not prove the old holder stopped, nor cancel an already-submitted request. Kubernetes warns its client-go election does not fence acting clients and says releasing on cancellation is unsafe unless guarded work is complete. Renewal helps liveness/overlap but is not a stale-write barrier. ([Kubernetes client-go source](https://github.com/kubernetes/client-go/blob/master/tools/leaderelection/leaderelection.go), [Redis consistency guidance](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/)) |
| **Immutable result + conditional publish** | Write each attempt to an attempt/version-specific immutable key, then atomically move the visible pointer only if its expected version/generation still matches. This lets stale computation finish without replacing the current result. Amazon S3 supports conditional writes: `If-None-Match` prevents creating over an existing key, and `If-Match` rejects a write when the current ETag changed. ([Amazon S3 conditional writes](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html))                           | The conditional operation must guard the actual publication pointer or result consumers use. Immutable attempt files alone do not select the winner; a stale writer can still win an unguarded pointer update. S3 ETags/conditions are object-store specific and do not provide one transaction across S3 and a database. The pointer design is a synthesis from conditional-write semantics, not an S3 guarantee across systems.                                                                                                                                            |

## Choosing a protection

- Use **CAS/version predicates** to prevent lost updates or to make the database the arbiter of a claim/completion transition.
- Use **idempotency and uniqueness** when the same message/request may be retried or delivered concurrently.
- Use **outbox/inbox** when a committed database change must reliably produce or consume a message.
- Use **leases** to recover ownership after worker loss; pair them with write cancellation and a sink-enforced fence/CAS when stale work could corrupt results.
- Use **immutable output plus guarded publication** when computation is long and only one result should become visible.

These protections compose: for example, an outbox can deliver at least once, an inbox/unique key can absorb duplicate delivery, a lease can coordinate active workers, and a database generation check or fencing-aware sink can reject stale completion. The right combination depends on whether the protected effect is a database row, a broker message, an object, or an external side effect.
